# Supabase 지역 왕복 비교

2026-10-13 사용자 요청에 따른 임시 합성 데이터 벤치마크. 서울 신규 프로젝트 생성은 무료 활성 프로젝트 제한으로 거절되어, 사용자 추가 승인으로 서울 `ImaginArena`를 사용했다. 싱가포르는 기존 `naengtalk`다.

## 무엇을 측정하는가

- 함수 실행 지역(서울/싱가포르) × DB 프로젝트 지역(서울/싱가포르)의 네 조합.
- 동일 SQL 함수, 40개 가상 재고, 20개 가상 후보, 30개 가상 상세 재료를 사용한다.
- `single`: 재고 응답 크기의 1회 RPC.
- `ocr4`: 인증 응답 대체 1회 + 사용 제한 기록 대체 1회 + 캐시 읽기 대체 1회 + 캐시 쓰기 대체 1회.
- `menu8`: 인증 응답 대체 + 사용 제한 기록 대체 + 재고 조회 + 공개 후보 + 공유 후보 + 첫 상세 + 재작성 상세 + 관측 기록 대체 = 순차 8회.
- 각 조합의 첫 호출 1회는 별도 보관, 8회 경로 준비 호출 3회 제외, 각 프로필 30회 순서를 바꾸어 반복. 마지막으로 각 조합에서 4개 동시 요청을 3묶음 실행한다.
- `totalMs`는 Edge 함수 내부의 모든 RPC 응답 본문 수신까지의 시간이다. `clientMs`는 로컬 실행기에서 함수 응답까지의 시간이며 네트워크·함수 시작 비용도 포함한다.
- `SB_REGION`과 응답 헤더로 실행 지역을 확인하고, HTTP 실패·지역 불일치가 있으면 측정을 중단한다.

## 한계

실제 앱 SQL·RLS·Auth 검증·AI 생성·검색을 실행하는 전체 기능 테스트가 아니다. 실제 계정과 사용자 데이터를 쓰지 않고 왕복 횟수와 응답 크기를 재현한 비교다. 인증·사용 제한·관측 RPC는 동일한 합성 RPC로 대체하므로 실제 처리시간이 같다는 뜻이 아니다. 두 기존 프로젝트의 백그라운드 부하와 물리 서버는 통제할 수 없다. Postgres 17.6, shared_buffers 224 MiB, effective_cache_size 384 MiB, max_connections 60은 양쪽에서 같음을 확인했다.

현재 작업 트리의 `menu-chat/index.ts`는 Auth 1회 + 사용 제한/재고/공개 검색/공유 검색/첫 상세/재작성 상세/관측 기록의 DB 요청 최대 7회로 서버 왕복 8회를 만든다. AI는 분류 1회 + 생성/재작성 최대 2회이며 이 측정에서 제외했다. `purchase-ocr`와 `inventory-parse`의 DB 관련 왕복은 Auth 포함 최대 4회이며 상품 40개라도 캐시 읽기와 쓰기는 묶어서 각각 1회다. 소진일 외부 AI 검색/추정은 DB 왕복 횟수와 구분한다. 이 개수는 로컬 코드 기준이며 아직 미배포 변경이 포함될 수 있다.

## 실행과 정리

1. 임시 객체가 없는지 확인한 뒤 두 프로젝트 각각에 `setup.sql` 실행.
2. 이 디렉터리를 workdir로 `region-bench-20261013` 하나만 배포. 기존 서비스 함수를 배포하지 않는다.
3. `BENCH_SUPABASE_CLI`에 실행 가능한 CLI 경로를 지정하고 `node tools/region-benchmark/run.mjs` 실행.
4. `results.json`은 원시 시간과 상태, `summary.json`은 중앙값/P95/평균/최대값을 담는다. 키는 CLI 출력에서 메모리로만 읽으며 저장하지 않는다.
5. 두 프로젝트에서 해당 임시 배포 함수만 삭제하고 `cleanup.sql` 실행.
6. 임시 스키마, 테이블, 공개 RPC, 배포 함수가 없는지 확인한다. 합성 테스트 데이터는 삭제하지만 공급자의 함수 실행/접속 로그와 CLI의 표준 로그인 역할 관리는 따로 삭제하지 않는다.

정리 SQL은 특정 이름의 함수·테이블·스키마만 제거하며 CASCADE나 서비스 데이터 삭제를 사용하지 않는다. 재실행 시 기존 측정 원시 결과는 덮어쓰므로 필요한 결과를 먼저 보관한다.
