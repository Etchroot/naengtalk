# 앱 테스트와 오류 추적

## QA-001 삼겹살 된장찌개 요청 실패 (2026-10-11)

- 상태: 사용자 정정으로 실제 요청과 재고는 모두 `삼겹살` 정상 표기. 이름 오타 원인 판단을 철회함. DB 후보 없음 → Terra 생성 → 검증 실패 → 재작성 → 재검증 실패 경로 재현 완료. 운영 요청의 모델 출력·최종 검증 사유는 미확인. 수정·배포 미실행.
- 사용자 제보: 삼겹살과 된장이 재고에 있는데 삼겹살을 이용한 된장찌개를 요청하면 `현재 재고로 만들 수 있는 레시피를 찾지 못했습니다` 안내가 나타남. 냉동삼겹살 명칭 또는 부재료 부족 가능성을 제기함.
- 후속 답변에서 사용량보다 충분한 g 단위 재고와 미래 소비기한을 확인했다. 사용자가 대화 답변의 오타를 정정했으며 실제 요청·재고는 정상 `삼겹살` 표기다. 앞선 실제 앱 오타 확인 해석은 잘못된 판단이었다. 사용자 재고의 상세 수량·날짜는 이 문서에 기록하지 않는다.
- 운영 DB 관측 trace와 실제 모델 결과, 요청 ID는 조회하지 못했으므로 아래 재현을 사용자 장애의 확정 원인으로 간주하지 않는다.

### 확인한 경로와 재현

사용자 재고가 아닌 합성 재고(냉동삼겹살 500g, 된장 200g, 미래 소비기한)를 사용했다. 원격 AI·DB 호출을 mock으로 대체해 로컬 `menu-chat` handler까지 실행했다.

| 입력 조건 | 확인 결과 |
| --- | --- |
| 삼겹살 150g + 된장 25g + 물 400ml | HTTP 200. 냉동삼겹살에 삼겹살 이름이 매칭되고 구매 0개로 통과 |
| 된장만 1T로 표시, 실제 재고는 g | 재고 검증에서 된장을 부족 품목으로 판정. 같은 결과를 재작성에서도 반환하면 HTTP 422와 제보 문구 재현 |
| 재고에 없는 두부·애호박 추가 | 구매 2개로 탈락. 같은 결과를 재작성에서도 반환하면 HTTP 422와 제보 문구 재현 |
| 된장 재고가 10g인데 레시피는 25g 사용 | 순수 검증에서 된장 부족 판정 |
| 냉동삼겹살 재고 단위가 개인데 레시피는 g 사용 | 순수 검증에서 삼겹살 부족 판정 |
| 냉동삼겹살 소비기한 경과 | 추천 대상에서 제외되어 순수 검증에서 삼겹살 부족 판정 |

### 확인된 개선 대상

1. **검색 이름 일치 방식 차이:** `recipe-routing.ts`의 `inventorySearchTerms`는 `냉동삼겹살`만 검색어로 보내고 `삼겹살`을 별도로 추가하지 않는다. 공공·공유 검색 RPC는 exact match라 일반 삼겹살 후보의 매칭 점수가 낮아질 수 있다. 최종 재고 검증은 공백 제거·부분 일치라 냉동삼겹살을 정상 매칭한다. 검색 실패만으로 최종 오류가 결정되지는 않고 Terra 생성 경로가 존재한다.
2. **부족과 단위 불일치를 같은 값으로 처리:** `recipe-inventory-guard.ts`의 `comparable`은 T/t를 ml로 바꾸지만 g와 ml 사이 환산은 하지 않는다. 된장 재고가 g인데 모델이 T로 출력하면 보유량과 무관하게 부족 처리된다. 된장에 임의의 밀도를 적용하는 수정은 근거가 없으므로 피하고 재고 단위 유지·재작성 지침부터 확인해야 한다.
3. **구매 허용과 재작성 지침 충돌(2026-10-13 로컬 수정):** 구매 1개 후보 분기를 제거하고 실제 준비 재료를 구매 0개로 고정했다. 재고 밖 재료는 구조화 선택 팁으로만 허용한다.
4. **실패 원인 소실:** 요청 재료 누락·비조리 결과·구매 초과는 사용자에게 같은 문구로 반환되고, 재작성 실패 후에는 최종 오류를 `PURCHASE_LIMIT_EXCEEDED`로 덮어쓴다. 현재 trace의 `repair_reason`은 첫 실패 사유이며 마지막 검증 사유·부족 품목은 보존되지 않는다. trace만으로 g/T 불일치와 실제 부재료 부족을 구분할 수 없다.
5. **신규 AI 생성의 구매 1개 허용 경로 누락(정책 대체):** 실제 레시피에서 구매 재료를 허용하지 않는 2026-10-13 결정으로 더 이상 결함이 아니다. 선택 재료 한 건은 준비 재료와 별도 필드로만 반환한다.
6. **재작성에서 보유 부재료 누락 가능:** `repairPantry`는 직접 요청한 재료와 고정 조미료 목록을 중심으로 재고를 줄인다. 요청에 없는 두부·애호박·양파 등이 실제 재고에 있어도 재작성 입력에서 빠질 수 있다. 이 사용자 요청에서 발생했는지는 미확인.

### 검증과 후속

- 순수 도메인 합성 입력 7개 및 Edge handler 합성 시나리오 3개에서 예상 결과를 assert로 확인했다.
- `node --test tests/recipe-inventory-guard.test.ts tests/recipe-routing.test.ts tests/recipe-policy.test.ts tests/menu-chat-edge.test.ts`: 32개 통과, 실패 0개.
- 정상 이름·g 단위·미래 소비기한 입력은 삼겹살·된장 g 사용 레시피가 구매 0개로 통과. 앞선 오타 입력 실험은 사용자가 정정했으므로 사용자 장애 원인 근거에서 제외한다.
- 최신 mock Edge 재현: 공공·공유 DB 후보 모두 없음, 정상 삼겹살·된장 재고, AI가 재고에 없는 두부 1개를 포함한 레시피를 두 번 반환하는 입력. Terra 호출 2회, 각 시도 구매 제한 0개, candidate_origin=AI_GENERATED, repair_reason=PURCHASE_LIMIT_EXCEEDED, HTTP 422와 제보 문구를 확인했다. AI 생성이 실행되지 않는 현상과 생성 결과가 검증에서 탈락하는 현상을 구분한다.
- 최신 기존 테스트: `node --test tests/menu-chat-edge.test.ts tests/recipe-inventory-guard.test.ts` 19개 통과. DB 후보가 없을 때 신규 Terra 생성 성공 경로 테스트 포함.
- 제보 문구는 현재 코드에서 Terra 생성 및 재작성 이후 검증 실패 경로에서 반환된다. DB 조회 자체의 장애·AI 연결 미설정·시간 초과는 다른 문구로 반환된다. 실제 운영 요청의 후보 출처와 첫 검증 사유는 trace 조회 전까지 단정하지 않는다.
- 후속 개선은 production Edge·웹 배포 후 오류 추적 번호로 실제 요청의 최초·재작성·최종 실패 단계를 확인한다. 오타 자동 병합을 이 장애의 수정으로 추진하지 않는다.
- 운영 trace는 계정 식별자를 문서·로그에 남기지 않고 해당 요청의 status·repair_reason·error_code·후보 출처·모델 호출 수만 확인할 것.
- 실제 모델 원문을 영구 관측에 추가하지 않는다. 원인을 더 구분하려면 원문 없는 최종 검증 오류 유형·단위 불일치 개수 등 별도 관측 설계를 검토할 것.
