# OpenAI Vision 구매내역 OCR 설계

## 목표

Android와 웹의 게스트 심사 환경에서 같은 OpenAI API 경로로 구매내역 캡처를 읽고, 화면에 보이는 텍스트와 재고 등록 후보를 사용자가 비교한 뒤 확정할 수 있게 한다. 사용자가 제공한 `r1.jpg`~`r5.jpg`를 재현 가능한 데모 입력으로 포함하고 `icon.png`를 앱 아이콘과 홈 화면 아이콘에 적용한다.

## 범위

- 홈·재고의 기존 등록 팝업에 `구매내역 캡처 등록` 버튼을 추가한다.
- 게스트는 번들에 포함된 R1~R5 미리보기 중 한 장을 선택한다.
- Android와 웹 모두 인증된 Supabase `purchase-ocr` Edge Function을 호출한다.
- 함수는 `gpt-5.6-luna`의 이미지 입력과 strict structured output을 사용한다.
- 화면에 보이는 상품 텍스트만 인식하고 상품 사진의 외형은 상품 판별 근거로 사용하지 않는다.
- 결과 화면은 `인식한 원문`과 `냉톡 재고 등록 후보`를 분리해 보여준다.
- 사용자가 최종 `재고에 등록`을 누른 항목만 자신의 `inventory_lots`에 기록한다.
- 실제 갤러리·카메라 선택, 종이 영수증 촬영 보정과 고급 편집 UI는 이 데모 다음 단계로 둔다.

## 에셋 배치

- `icon.png` → `mobile/assets/images/icon.png`를 교체하고 홈 좌상단 `Image`에도 사용한다.
- `r1.jpg`~`r5.jpg` → `mobile/assets/demo/purchases/`로 이동한다.
- 정적 `require()` 목록으로 번들에 포함해 Android와 웹에서 같은 샘플을 보여준다.

## 사용자 흐름

1. 게스트가 홈의 `구매내역 등록` 또는 재고의 `재고 등록`을 누른다.
2. 공용 등록 팝업에서 `구매내역 캡처 등록`을 선택한다.
3. R1~R5 이미지 카드 중 하나를 누른다.
4. 앱은 이미지를 data URL로 읽고 크기·MIME을 검사한 뒤 `purchase-ocr`을 호출한다.
5. 처리 중에는 중복 제출을 막고 `구매내역을 읽고 있어요…` 상태를 표시한다.
6. 결과 화면 상단에서 인식 원문을 스크롤로 확인한다.
7. 하단에서 식품명, 총수량, 단위, 권장 소진일과 `확인 필요` 여부를 확인한다.
8. `재고에 등록`을 누르면 등록 가능한 항목을 현재 사용자 재고에 넣고 재고 탭으로 이동한다.
9. 오류가 발생해도 선택한 샘플을 유지하고 재시도할 수 있다.

## 서버 API

### 요청

인증된 `POST /functions/v1/purchase-ocr` 요청은 다음 값을 받는다.

- `imageDataUrl`: `data:image/jpeg;base64,...` 또는 `data:image/png;base64,...`
- `sampleId`: `r1`~`r5`; 관측과 데모 결과 식별용이며 파일 접근 권한으로 사용하지 않는다.

서버는 JWT를 검증하고 사용자별 하루 10회 제한을 원자적으로 적용한다. data URL MIME과 디코딩 전 길이를 검사하고 5MB를 넘는 요청은 거부한다.

### OpenAI 요청

- 모델: `gpt-5.6-luna`
- API: Responses API
- 이미지 상세: `original`
- 추론 강도: `none`
- 저장: `store: false`
- 최대 출력: 2,000토큰
- 시간 제한: 35초
- 웹 검색: 사용하지 않음

모델은 UI 텍스트 중 주문 상품명·옵션·규격·구매수량·구매일만 추출한다. 가격, 버튼, 배송 문구와 상품 이미지 내용은 재고 후보에서 제외한다.

### 응답

```text
rawText: 화면에서 인식한 구매 관련 원문
items[]:
  productName: 화면의 원상품명
  foodName: 냉톡용 식품명
  quantity: 계산된 총수량 또는 null
  unit: g | ml | 개 | 대 | null
  category: tofu | leafy | vegetable | meat | frozen | pantry | prepared | unknown
  confidence: 0~1
  needsReview: boolean
  note: 계산 또는 확인 사유
```

클라이언트와 서버는 같은 런타임 검증 계약을 사용한다. 음수·0·지원하지 않는 단위·지나치게 긴 텍스트·과도한 항목 수는 거부한다.

## 권장 소진일

AI는 식품 카테고리만 분류하고 날짜 산술은 코드가 담당한다. 공식 소비기한이 캡처에 없으므로 다음 보수적 냉장 기준으로 `권장 소진일(추정)`을 만든다.

- 두부 3일
- 잎채소·버섯 5일
- 대파 등 일반 채소 7일
- 생육 2일
- 감자·마늘 등 저장 채소 14일
- 냉동식품 30일
- 실온 가공식품·소스 30일
- 분류 불명 또는 수량 불명은 `확인 필요`로 표시하고 자동 등록에서 제외한다.

기준일은 캡처에서 신뢰 가능한 구매일·도착일이 있으면 그 날짜, 없거나 이미 과거이면 등록 당일을 사용한다. 화면에는 공식 소비기한이 아닌 `권장 소진일(추정)`임을 명시한다.

## 재고 등록

클라이언트는 AI가 제시한 날짜를 직접 쓰지 않는다. 검증된 카테고리와 기준일을 결정적 함수에 넣어 권장 소진일을 계산한다. 등록 요청은 현재 사용자의 JWT와 RLS를 사용하며, 서버가 `owner_id`를 확정한다. `needsReview=false`이고 지원 단위와 양수 수량이 있는 항목만 일괄 등록한다.

## 개인정보와 비용 통제

- 원본 이미지를 Supabase Storage, DB, 로그 또는 OpenAI 저장 응답에 남기지 않는다.
- 클라이언트가 사용자의 명시적 버튼 동작 때만 전송한다.
- Edge Function은 이미지 내용과 API 오류 본문을 로그로 출력하지 않는다.
- R1~R5와 유사한 1080×2143 이미지 70장은 Luna 이미지·텍스트 토큰을 포함해 약 `$0.10~0.25`, 재시도를 넉넉히 포함해 `$0.50` 이내를 목표로 한다.
- OpenAI 프로젝트의 `$20` 월 한도와 별도로 사용자별 하루 10회 OCR 제한을 둔다.

## OCR 검증 문서

`docs/OCR_SAMPLE_RESULTS.md`에 각 샘플별로 다음을 기록한다.

1. 화면에서 인식한 원문
2. 냉톡에 등록될 구조화 결과
3. 잘림·수량 불명·묶음 계산 등 검토가 필요한 지점

실제 API 배포 전 작성한 내용은 `시각 분석 기준선`으로 표시하고, API 연결 후 같은 이미지의 실응답으로 교체하거나 나란히 비교한다. 모델 성능을 검증하지 않은 수기 정답을 실제 API 결과처럼 표현하지 않는다.

## 오류 처리

- 인증 실패: 다시 로그인 안내
- 크기·MIME 오류: 지원 형식과 5MB 제한 안내
- OpenAI 시간 초과·과금·모델 오류: 이미지를 유지하고 재시도 안내
- 구조화 출력 실패: 재고를 변경하지 않고 실패 상태 표시
- 등록 일부 실패: 전체를 다시 읽지 않고 검수 결과를 유지한다.

## 검증

- 계약 단위 테스트: 요청 제한, 응답 파싱, 수량·단위 거부, 카테고리별 날짜 계산
- 기존 전체 Node 테스트와 TypeScript 검사
- Android·웹 정적 export
- 실제 배포 후 R1~R5 중 최소 2장 실호출 비교
- 등록 전후 재고 증가와 RLS 사용자 격리 확인

전체 웹·APK E2E는 사용자의 요청대로 최종 배포 직전에 수행한다.

## 사용자가 직접 해야 하는 작업

1. Supabase Edge Function Secrets에 `OPENAI_API_KEY` 값을 저장한다.
2. Supabase CLI 배포를 위해 로컬에서 `supabase login`에 사용할 개인 access token을 본인만 보이는 환경에 등록한다.

API 키와 Supabase access token은 Codex 채팅, GitHub 또는 앱 환경 파일에 전달하지 않는다.
