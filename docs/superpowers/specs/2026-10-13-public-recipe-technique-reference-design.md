# 공공 레시피 조리 기술 참고 구조 설계

- 작성일: 2026-10-13
- 상태: 로컬 구현·검증 완료, 배포 대기
- 범위: `menu-chat`의 공공 레시피 검색·개인화·검증 경로

## 1. 목적

공공 레시피는 사용자의 재고가 원본 재료 전체를 충족할 때 그대로 제공하는 완성 레시피가 아니다. 사용자 요청과 가까운 실제 조리 사례에서 재료 투입 순서, 가열 방식, 조리 시간, 양념 구조와 안전 조건을 참고하기 위한 근거다. 최종 레시피는 사용자가 직접 요청한 재료와 현재 보유 재고만으로 새로 구성한다.

성공 기준은 다음과 같다.

- 공공 레시피 원본에 재고에 없는 부재료가 있어도 조리 기술 참고 후보로 사용할 수 있다.
- 사용자가 직접 말한 재료는 최종 레시피에 모두 포함한다.
- 최종 필수 재료는 현재 재고와 필요할 때의 물·식수만 허용한다.
- 재고에 없는 재료는 최대 한 건의 선택 팁으로만 안내하고 조리·차감에는 포함하지 않는다.
- 공공 후보 조회 때문에 별도의 AI 호출을 추가하지 않는다.
- 공공 DB 참고 여부와 AI 단독 생성 여부를 콘텐츠 없이 관측할 수 있다.

## 2. 비목표

- 공공 레시피 원문을 그대로 사용자에게 제공하지 않는다.
- 모든 공공 레시피를 하나의 대형 프롬프트 파일로 합치지 않는다.
- 공공 레시피의 원본 재료량을 사용자에게 강제하지 않는다.
- 웹 검색을 레시피 생성 경로에 다시 도입하지 않는다.
- 물을 모든 레시피에 자동으로 추가하지 않는다.

## 3. 후보 검색과 채택

검색 입력은 `요청 메뉴명`, `사용자가 명시한 재료`, `현재 재고명`으로 분리한다. 공공 후보는 다음 우선순위로 정렬한다.

1. 사용자가 명시한 재료 포함률
2. 요청 메뉴명 또는 조리 방식 일치도
3. 현재 재고와 후보 재료의 중복도
4. 조리 단계와 조리 방식 정보의 완전성

공공 후보의 모든 재료가 재고에 있어야 한다는 기존 `구매 0개 후보` 조건은 공공 후보 채택 단계에서 제거한다. 대신 다음의 결정적 최소 조건을 적용한다.

- 메뉴명이 있는 요청: 후보 이름이 요청 메뉴와 정확히 일치하거나 한쪽이 다른 쪽을 포함해야 한다. 명시 재료가 함께 있으면 그중 한 개 이상도 후보에 있어야 한다.
- 재료 중심 요청: 명시 재료가 1~2개면 전부, 3개 이상이면 최소 2개이면서 60% 이상이 후보에 있어야 한다.
- 막연한 요청: 현재 재고와 후보 재료가 최소 2개 일치하고 후보 전체 재료의 30% 이상이 일치해야 한다.
- 모든 경로에서 설명이 있는 조리 단계가 최소 2개 있어야 한다.

최소 조건을 통과한 후보는 명시 재료 포함률, 메뉴명 일치, 재고 중복률, 단계 완전성 순으로 정렬한다. 동률이면 명시 재료 일치 개수, 재고 일치 개수, 안정적인 레시피 ID 순으로 결정한다. 조건을 만족하는 공공 후보가 없으면 기존 공유 추천 레시피에 같은 기준을 적용하고, 그것도 없으면 AI 단독 생성으로 전환한다. 공공·공유 후보 모두 최종 재료의 근거가 아니라 조리 참고자료로만 취급한다.

## 4. AI에 전달하는 참고 정보

선택한 후보 한 건만 다음의 제한된 `techniqueReference` 형태로 Terra에 전달한다.

- 검증된 원천 구분과 레시피 ID
- 레시피명과 조리 방식
- 순서가 보존된 조리 단계
- 조리 팁
- 단계 이해에 필요한 원본 재료명

이미지 URL, 영양정보, 원문 재료 문자열과 검색에 불필요한 메타데이터는 전달하지 않는다. 프롬프트는 참고 후보의 재료를 복제하지 말고 조리 원리만 차용하도록 명시한다. 이 변환은 결정적 코드로 수행하며 후보 요약을 만들기 위한 별도 모델 호출은 하지 않는다.

## 5. 최종 레시피 구성 규칙

Terra는 다음 재료 집합 안에서 최종 레시피를 작성한다.

- 사용자가 직접 요청한 재료
- 사용자의 현재 재고
- 조리상 실제로 필요한 경우의 물 또는 식수

물·식수는 무제한 가상 기본 재료다. 재고에 없어도 사용할 수 있고 구매 필요 판정과 완료 후 차감에서 제외한다. 다만 물이 필요하지 않은 스테이크, 볶음, 튀김 등의 요리에는 넣지 않는다. 육수, 우유, 식용유와 소스는 물로 간주하지 않으며 실제 재고 검증을 받는다.

재고에 없는 재료는 `optionalIngredientTip` 한 건 이하로만 제시할 수 있다. 선택 재료가 없어도 레시피의 모든 단계가 완성되어야 하며, 해당 재료는 `ingredients`, 필수 단계와 사용량 차감에 들어가지 않는다.

## 6. 결정적 검증과 재작성

모델 응답 후 서버가 다음을 검증한다.

- 요청 재료 전부 포함
- 재고 재료명·단위·사용량 충족
- 물·식수 이외의 미보유 필수 재료 없음
- 등록 알레르기 미포함
- 실제 조리가 되는 한 끼인지 확인
- 허용된 조리도구와 안전 조건 충족
- 선택 재료가 필수 재료나 차감 목록에 섞이지 않음

최초 결과가 실패하면 요청당 한 번만 재작성한다. 재작성은 문제가 된 공공 후보를 다시 강제하지 않고, 요청 재료·관련 재고·검증 피드백만 전달하는 AI 단독 복구 경로를 사용한다. 재작성도 실패하면 추적 번호가 포함된 명확한 실패 응답을 반환한다.

## 7. 지연 시간과 비용

요청당 공공 DB 후보 검색과 후보 상세 조회는 현재와 같은 서버 호출 수를 유지한다. 모델 호출은 정상 시 Terra 한 번, 검증 실패 시 재작성 한 번으로 제한한다. AI 요약 호출과 웹 검색은 추가하지 않는다. `techniqueReference`는 후보 한 건의 필요한 필드만 포함하고 길이를 제한해 입력 토큰 증가를 통제한다.

## 8. 관측

대화 원문이나 레시피 콘텐츠를 저장하지 않고 다음의 제한된 진단값을 남긴다.

- 최초 참고 원천: `MFDS`, `MAFRA`, `SHARED_AI`, `AI_GENERATED`
- 최종 성공 경로: `public_technique`, `shared_technique`, `ai_only`, `ai_repair`
- 후보 점수 구간과 재작성 여부
- 기존 단계별 지연, 모델 호출 수, 토큰 수와 실패 코드

이 값으로 공공 DB 후보 적중률, 참고 후 재작성률, AI 단독 생성률과 경로별 지연을 비교한다. 사용자 입력, 재고명, 후보 제목과 생성 레시피는 관측 DB에 저장하지 않는다.

## 9. 테스트

단위 테스트:

- 후보 원본에 미보유 부재료가 있어도 명시 재료와 조리법이 맞으면 채택
- 공공 후보의 모든 재료가 재고와 일치하지 않아도 검색 점수가 계산됨
- 물은 필요한 레시피에서만 허용되고 재고·차감 검증에서 제외
- 육수·우유·기름은 물 예외를 받지 않음
- 선택 재료가 실제 재료와 차감 목록에 들어가지 않음

통합 테스트:

- 공공 기술 참고 → Terra 개인화 → 재고 검증 성공
- 공공 기술 참고 결과가 미보유 재료를 넣음 → AI 단독 재작성 성공
- 공공 후보 정확도 미달 → 처음부터 AI 단독 생성
- 요청 재료 누락·재고 초과·알레르기 포함 결과 차단
- 공공 참고 경로와 AI 단독 경로의 관측 필드 기록

회귀 검증:

- 전체 Node 테스트
- 엄격한 TypeScript 검사
- Expo 웹 정적 export
- 배포 전 원격 공공 후보 적중·AI fallback 스모크 테스트

## 10. 변경 경계

구현은 후보 검색 RPC와 마이그레이션, 후보 정렬·참고자료 변환, `menu-chat` 오케스트레이션, 프롬프트 지침, 관측 필드, 테스트와 관련 기술 문서만 수정한다. 앱 화면과 재고 저장·차감 트랜잭션 계약은 변경하지 않는다.
