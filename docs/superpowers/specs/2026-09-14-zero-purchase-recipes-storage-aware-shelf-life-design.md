# 구매 0개 우선 레시피와 보관 상태별 공용 소진일 설계

작성일: 2026-09-14 · 상태: 구현 및 배포 완료, 실사용 검수 대기 (2026-09-19)

## 목표와 확정 기준

- 모든 추천에서 **추가 구매가 0개인 실행 가능한 레시피를 최우선**으로 한다. 공공 레시피·공유 레시피라는 출처나 메뉴 이름의 일치도보다 구매 0개가 우선한다.
- 구매 0개 레시피를 만들 수 없을 때만 구매가 필요한 재료 최대 1개를 허용한다. 필수 구매 재료가 2개 이상인 레시피는 응답하지 않는다.
- 보유 재료, 특히 권장 소진일이 가까운 재료를 사용한다. 원본 레시피의 비핵심 재료는 생략하고 조리상 타당한 재고 재료로 대체하되, 음식 이름·조리법을 허위로 유지하지 않는다.
- `냉동`이라고 명시된 **모든 식품**은 같은 식품의 냉장·상온 보관과 별도 기준으로 권장 소진일을 조회·보존한다. 삼겹살만의 예외 규칙을 만들지 않는다.
- 기존 `public.shelf_life_rules`가 공용 DB이므로 새 중복 테이블을 만들거나 기존 규칙을 지우지 않는다.
- 이전 사용자 지시대로 실제 테스트와 명시적 요청 전에는 Git 커밋·푸시하지 않는다.

## 현재 문제와 원인

1. `chooseRecipeCandidate`가 요청 메뉴명의 완전 일치(`name_score=100`)만으로 후보를 채택한다. 냉장고에 없는 재료 수나 실제 조리 가능성이 채택 조건이 아니다.
2. Terra 지침은 필수 재료가 없으면 `requiredPurchase=true`로 표시하라고 하지만 상한을 정하지 않는다. 최종 응답 검증은 알레르기만 확인하고 구매 수·재고 대응 관계는 확인하지 않는다.
3. 이미 공용 `shelf_life_rules` 조회 → 근거 있는 웹 검색 → 저장 경로가 있다. 검색 근거가 없으면 `pantry` 등 식품군 기본 30일을 사용하고, 화면 검수 변환은 값이 채워져 있다는 이유로 이를 확정 가능한 날짜처럼 다룰 수 있다.
4. 직접 입력·OCR 구조화의 `foodName`은 브랜드·수식어를 제거한다. 원본의 `냉동`이 재고명에서 사라지거나 분류 모델이 `frozen`을 선택하지 않으면 냉장 기본 조회로 합쳐진다. 재고 lot에는 보관 방식 자체를 보존하는 컬럼이 없다.

## 레시피 검색·생성 경로

구매 필요 품목 수를 최상위 정렬 키로 두고 그 안에서 출처 순서를 적용한다.

| 우선순위 | 경로 |
| --- | --- |
| 1 | 구매 0개로 개인화 가능한 공공 DB 후보 |
| 2 | 구매 0개로 개인화 가능한 동의 공유 DB 후보 |
| 3 | 구매 0개를 목표로 한 Terra 신규 생성 |
| 4 | 위 경로에서 가능한 답이 없을 때만 구매 1개 이하의 공공·공유 후보 또는 Terra 생성 |

- 후보 검색은 현재의 구조화 재료 인덱스를 유지하되, 메뉴 이름 일치만으로 채택하지 않는다. 재고와 단위·수량을 비교한 실현 가능성, 사용 가능한 조리도구, 알레르기, 구매 예상 품목 수를 먼저 본다. 같은 구매 수 내에서 임박 재료 사용과 메뉴 의도 일치도를 가중한다. 공공 후보의 부족한 부재료는 Terra 개인화 단계에서 생략·대체할 수 있으므로, 후보 단계는 보수적인 사전 점수이고 최종 합격 판정은 생성 후 서버가 한다.
- Terra 지침은 `재고 재료 우선 → 비핵심 재료 제거 → 임박 재료의 타당한 대체 → 그래도 필요한 핵심 재료만 구매` 순서로 설계한다. 물은 구매 대상에서 제외할 수 있지만 간장·된장·소금 등 식품·조미료는 등록 재고가 없다면 무상 보유품으로 가정하지 않는다.
- 서버는 AI가 반환한 `inInventory`·`requiredPurchase` 표시를 신뢰하지 않는다. 구조화 재료를 현재 사용자 lot의 `ingredient_key`, 명칭, 단위 및 사용 가능량과 대조하고, `T=15ml`, `t=5ml` 같은 기존 환산을 적용한다. 없는 재료 또는 부족한 양의 식품을 구매 필요로 계산한다. 단계 설명에 필요한 식품이 재료 목록에서 빠져 있으면 생성 결과를 재검토 대상으로 본다. 알레르기와 도구 제약도 기존 검사를 유지한다.
- 구매 2개 이상이거나 재고에서 충당할 수 없는데 구매가 0개로 표기된 결과는 사용자에게 반환하지 않는다. 제한된 횟수로 재작성/재생성하고, 여전히 기준을 통과하지 못하면 불가능한 레시피 대신 이유를 알려준다.
- 사용자가 특정 메뉴를 요청했더라도 구매 0개로 그 메뉴를 만들 수 없고 다른 0개 메뉴가 가능하다면, 다른 메뉴를 한 가지만 제시하고 원 요청과 다른 이유를 짧게 설명한다. 0개 대안이 없을 때만 구매 1개 선택지를 제시한다.
- 기존 공공 CSV나 공유 레시피 원본은 변경하지 않는다. 추천 결과의 변형은 요청 시에만 수행한다.

## 보관 상태별 공용 권장 소진일

1. 입력의 원문 구절(`productName` 또는 직접 입력 원문)에서 `냉동`, `냉장`이 명시되었는지 결정적 규칙으로 식별한다. `냉동`은 식품군과 무관하게 `storage_method=frozen`으로 우선 적용한다. 명시가 없을 때에만 기존 식품군 기본값을 사용한다. 같은 구절에서 충돌하는 상태가 나오면 사용자 확인 대상으로 남긴다.
2. `foodName`은 정규화 식품명으로 유지하고 보관 상태를 별도 필드로 유지한다. 공용 DB 조회 키는 기존 `(canonical_key, storage_method, package_state)`를 사용하므로 `삼겹살|frozen|unopened`와 `삼겹살|refrigerated|unopened`는 서로 다른 규칙이다. 이 규칙은 채소·생선·조미료·가공식품에도 동일하게 적용한다.
3. 등록 검수와 이후 조회에서도 차이를 잃지 않도록 `inventory_lots`에 보관 방식을 저장한다. 기존 lot은 근거 없이 냉동·냉장으로 일괄 재분류하지 않고, 새 등록부터 확정된 상태를 기록한다. 화면에는 재료명 옆에 간결한 보관 상태를 표시하고 검수에서 잘못 인식한 상태를 고칠 수 있게 한다.
4. 공식 포장 표시일이나 사용자가 직접 입력한 날짜는 해당 lot에만 적용하고 공용 일반 규칙으로 학습하지 않는다. 그 외에는 공용 DB의 유효한 상태별 규칙을 먼저 읽고, 없는 조합 또는 오래된 규칙만 서버의 제한된 웹 검색으로 확인한다. 실제 검색 결과의 HTTPS 근거·기간·보관 조건을 검증한 항목만 공용 DB에 upsert한다. 이후 다른 사용자에게 같은 조합의 규칙을 재사용한다.
5. 검색 실패·출처 불충분 시 `pantry=30일` 같은 임시값을 확정된 소진일로 제시하지 않는다. 날짜는 비워두고 사용자가 제품 표기·보관 상태를 확인해 입력한 뒤 등록하도록 한다. 사용자 임의 날짜는 공용 DB에 기록하지 않는다.
6. 기존 식품군 기본값은 내부 안전 가이드/재시도 조건으로만 남길 수 있으며, 검증된 공용 규칙이나 사용자 입력을 대신해 자동 등록 날짜가 되어서는 안 된다. 기존 공용 규칙은 삭제하지 않고 출처·상태가 확인된 것만 유지·사용한다.
7. 구매내역 OCR, 직접 입력, 채팅을 통한 식품 추가가 동일한 상태별 소진일 resolver를 사용한다. OpenAI·service role 키는 Edge Function에만 보관하고 클라이언트에 전달하지 않는다.

## 오류 처리와 검증

- 공용 DB 조회 실패와 웹 검색 실패는 서버에서 구분해 기록하되 사용자에게는 근거 없는 날짜를 확정값으로 표시하지 않는다. 출처 조회 실패가 일시적이면 재시도 가능하며 사용자는 날짜를 직접 입력할 수 있다.
- 신규 테스트는 `이름은 일치하나 구매 10개` 후보 탈락, `공공 1개 구매`보다 `공유 또는 Terra 0개 구매` 우선, 임박 재료 대체, 구매 최대 1개 하드 가드, 알레르기·도구 유지, `냉동 X`와 `냉장 X`의 다른 캐시 키, 기존 `X` 기본 보관 구분, 직접 입력·OCR·채팅 추가의 공통 조회, 검색 실패 시 빈 날짜·등록 차단을 포함한다.
- 원격 테스트는 새 익명 게스트가 재고를 등록한 뒤 0개 구매 레시피를 받는지, 다른 게스트가 같은 보관 상태 규칙을 재사용하는지, 냉동/냉장 동명 식품의 날짜가 섞이지 않는지를 확인한다. 마지막에 Expo 웹을 배포하고 사용자 수동 검수를 요청한다. Android APK는 별도 최종 빌드 일정대로 유지한다.

## 범위 밖

- 공공 CSV 재전처리, 레시피 웹 검색 재도입, 사용자별 다른 공용 소진일 DB 생성, 기존 재고 lot의 추정 일괄 수정, 외부 쇼핑몰 연동은 수행하지 않는다.
