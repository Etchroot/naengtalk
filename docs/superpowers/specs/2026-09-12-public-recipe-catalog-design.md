# 공공 레시피 카탈로그 설계

## 목표와 범위

식품의약품안전처(MFDS)와 농림축산식품부(MAFRA) 공공데이터를 전처리한 최종 CSV 3개를 Supabase PostgreSQL에 한 번 적재하고, 이후 레시피 추천이 이 카탈로그를 우선 검색할 수 있는 데이터 기반을 만든다. 카탈로그에서 충분히 정확한 후보를 찾지 못하면 웹 검색으로 전환하지 않고 `gpt-5.6-terra`가 레시피를 생성한다.

이번 작업 범위는 다음 1~5단계로 제한한다.

1. 현재 프로젝트와 기존 Supabase 구조 분석
2. 패키지·환경변수·배포 도구 확인
3. 레시피 카탈로그 스키마와 migration 작성
4. 일회성 CSV import 도구 작성
5. 로컬 CSV와 원격 DB의 데이터 무결성 검증

Expo 앱 UI, Supabase 클라이언트, 레시피 repository, AI 검색 우선순위 변경은 이번 범위에서 수정하지 않는다.

## 기존 구조와 충돌 회피

현재 `public.recipes`는 사용자별 AI 생성 레시피를 저장한다. `public.cooking_sessions`, `public.completed_recipes`, `complete_recipe_cooking()`, `reset_guest_demo()`가 이 테이블에 의존한다. 따라서 공공데이터 테이블을 `public.recipes`로 생성하거나 기존 테이블을 이름 변경하지 않는다.

공공데이터는 별도 비공개 스키마 `recipe_catalog`에 다음 이름으로 저장한다.

- `recipe_catalog.recipes`
- `recipe_catalog.ingredients`
- `recipe_catalog.steps`

이 구조는 요구한 테이블 이름과 관계를 유지하면서 사용자 생성 레시피와 공공 레시피의 수명주기·권한·식별자 형식을 분리한다.

## 입력 데이터 불변 조건

입력 파일은 프로젝트 루트의 다음 경로에 존재한다.

- `scripts/data/FINAL_recipes.csv`
- `scripts/data/FINAL_ingredients.csv`
- `scripts/data/FINAL_steps.csv`

`/scripts/`는 저장소 루트 기준으로 Git에서 제외한다. import 도구는 추적 가능한 `tools/`에 두며 CSV 값을 정제·정규화·재작성하지 않는다.

불변 조건은 다음과 같다.

- `recipe_id` 문자열을 그대로 PK와 FK에 사용한다.
- `MFDS_000028`, `MAFRA_000001` 형식을 변경하거나 재채번하지 않는다.
- 빈 CSV 필드는 nullable 컬럼의 SQL `NULL`로만 변환한다.
- `ingredients_raw`, `description_raw`, `ingredient_raw` 등 원본 보존 필드를 그대로 저장한다.
- `ingredients_raw`는 이후 검색 인덱스나 검색 로직에 사용하지 않는다.
- 데이터 행을 누락·합치기·분리하거나 기관 간 값을 보정하지 않는다.

사전 검증에서 확인한 현재 데이터 특성은 다음과 같다.

| 파일 | 행 수 | 고유 recipe_id | 중복 자연키 | FK orphan |
| --- | ---: | ---: | ---: | ---: |
| `FINAL_recipes.csv` | 1,684 | 1,684 | 0 | 해당 없음 |
| `FINAL_ingredients.csv` | 18,920 | 1,683 | 0 | 0 |
| `FINAL_steps.csv` | 9,542 | 1,684 | 0 | 0 |

`MFDS_000799`는 recipes와 steps에는 있지만 ingredients 행이 없다. 이는 현재 최종 CSV의 특성이므로 임의 보완하지 않고 그대로 적재한다.

## 인덱스

다중 재료 후보 검색과 상세 조회에 다음 인덱스를 생성한다.

- `ingredients(recipe_id)`
- `ingredients(normalized_name, recipe_id)`
- `ingredients(parent_ingredient, recipe_id)` — null 제외 partial index
- `ingredients(search_key, recipe_id)`
- `steps(recipe_id)`
- `steps(recipe_id, step_no)` — unique constraint의 인덱스로 충족
- `recipes(name)`

이번 데이터 규모에서는 정확 일치·prefix 후보 추출을 위한 B-tree를 우선한다. 한글 부분 문자열·오타 허용 검색용 trigram 인덱스는 실제 query 함수와 실행계획을 검증하는 7단계에서 필요할 때 추가한다.

## 권한과 접근 경계

`recipe_catalog`는 Data API의 기본 공개 스키마로 추가하지 않는다. 스키마와 모든 테이블의 권한을 `anon`, `authenticated`에서 회수한다. 클라이언트에 service role key나 DB 연결 문자열을 넣지 않는다.

이번 단계에서는 `public.import_recipe_catalog_batch(target_table text, rows jsonb)`와 `public.verify_recipe_catalog()`만 만든다.

- 두 함수 모두 `security definer`와 고정 `search_path`를 사용한다.
- 실행 권한은 `service_role`에만 부여한다.
- `target_table`은 `recipes`, `ingredients`, `steps` 세 값 외에는 거부한다.
- 동적 SQL로 테이블명이나 컬럼명을 조합하지 않고 테이블별 정적 upsert 분기를 사용한다.
- 검증 함수는 행 수, FK orphan 수, 자연키 중복 수만 반환하며 원문 데이터를 반환하지 않는다.

향후 앱 조회는 이 import 함수가 아니라 별도의 최소 결과 검색 RPC 또는 Edge Function을 사용한다.

## 일회성 import 흐름

추적 가능한 `tools/import_recipe_catalog.py`를 Python 표준 라이브러리만으로 구현한다. 별도 패키지 설치 없이 `csv`, `json`, `urllib.request`를 사용한다.

실행 시 필요한 서버 전용 환경변수는 다음과 같다.

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

이 값은 로컬 프로세스 환경에만 주입하며 `.env`, 문서, 명령 출력, Git에 기록하지 않는다. Expo 클라이언트의 `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`는 import 권한으로 사용하지 않는다.

도구의 처리 순서는 고정한다.

1. 세 CSV의 헤더를 명시된 스키마과 정확히 비교한다.
2. 전체 행을 읽어 로컬 무결성을 검사한다.
3. `recipes`를 PK 기준 배치 upsert한다.
4. `ingredients`를 `(recipe_id, ingredient_no)` 기준 배치 upsert한다.
5. `steps`를 `(recipe_id, step_no)` 기준 배치 upsert한다.
6. 원격 검증 RPC를 호출한다.
7. 예상 행 수와 실제 행 수, orphan과 중복을 비교하고 불일치 시 실패 종료한다.

동일한 최종 CSV를 다시 실행하면 기존 행이 갱신되고 identity 행이 추가되지 않아 결과 건수가 변하지 않는다. 현재 범위는 동일 스냅샷의 안전한 재실행을 보장한다. 미래 CSV에서 삭제된 행까지 동기화하는 전체 교체 기능은 자동 실행하지 않는다.

`--validate-only` 옵션은 네트워크와 DB 변경 없이 로컬 CSV만 검사하고 JSON 요약을 출력한다. 기본 실행은 `--apply`를 명시해야만 원격 쓰기를 수행하도록 해 오작동을 막는다.

## 데이터 무결성 검증

로컬 검증 실패 조건은 다음과 같다.

- 파일 또는 필수 헤더 누락
- 행 수가 `1684`, `18920`, `9542`와 다름
- `recipe_id`가 `^(MFDS|MAFRA)_\d{6}$` 형식이 아님
- recipes의 PK 중복
- ingredients의 `(recipe_id, ingredient_no)` 중복
- steps의 `(recipe_id, step_no)` 중복
- ingredients 또는 steps의 recipe FK orphan
- 필수 정수·numeric 값의 변환 실패

원격 검증 성공 조건은 다음과 같다.

- recipes = 1,684
- ingredients = 18,920
- steps = 9,542
- ingredients FK orphan = 0
- steps FK orphan = 0
- ingredients 자연키 중복 = 0
- steps 자연키 중복 = 0

검증 결과에는 원문 레시피, 재료, 조리 단계 내용을 출력하지 않는다.

## 테스트와 배포 순서

1. migration 계약과 import 도구의 `--validate-only` 동작을 실패 테스트로 먼저 작성한다.
2. migration과 import 도구를 최소 구현해 테스트를 통과시킨다.
3. 기존 전체 Node 테스트와 Supabase migration 정적 검사를 실행한다.
4. 연결된 Supabase 프로젝트에 migration을 적용한다.
5. 사용자가 로컬 환경에 제공한 service role key로 import를 한 번 실행한다.
6. 원격 검증 RPC 결과와 예상 건수를 대조한다.

원격 적용 전후에 CSV 원문이나 secret을 로그로 출력하지 않는다.

## 후속 단계 경계

6~8단계에서 다음을 별도 설계·구현한다.

- 기존 `mobile/src/services/supabase.ts`를 재사용한 서버 검색 경계
- `getRecipeById(recipeId)`
- `searchRecipesByIngredients(ingredients)`의 매칭 점수와 정렬
- `searchRecipesByName(keyword)`
- DB 검색 결과를 채택할 정확도 임계값과 판정 기준
- 정확도 임계값 미달 시 웹 검색 없이 `gpt-5.6-terra`로 레시피를 생성하는 fallback 계약
- 공공 레시피를 사용자 재고·알레르기·조리도구에 맞게 GPT가 재설계하는 입력 계약

이번 작업은 위 앱 조회·AI 연결 코드를 미리 변경하지 않는다. Terra 생성 프롬프트, 카탈로그 후보와 생성 결과의 구분, 안전 검증과 재시도 정책은 사용자가 후속 아키텍처 요구사항을 제공할 때 상세 설계한다.
