# 공용 권장 소진일과 다중 구매내역 검수 설계

## 목표

구매내역에서 정규화한 재고명별 권장 소진일을 공용 데이터베이스에서 먼저 조회하고, 기준이 없을 때만 웹 검색으로 생성·저장한다. 사용자는 샘플 또는 직접 선택한 여러 구매내역 이미지를 분석한 뒤 `재고명`, `수량`, `권장 소진일`을 한 화면에서 수정하고 최종 승인해야 재고가 변경된다.

## 선택한 접근

검토한 접근은 다음 세 가지다.

1. 코드에 고정된 식품 분류별 기간표만 사용: 빠르지만 `즉석밥`처럼 같은 가공식품 안에서 보관기간 차이가 큰 품목을 정확히 다루기 어렵다.
2. 매 등록마다 웹 검색: 최신 근거를 찾을 수 있지만 같은 재고명에 비용과 지연이 반복된다.
3. 공용 기준 우선 조회 후 누락 항목만 검색·저장: 첫 조회에만 비용이 들고 이후 사용자가 기준을 재사용할 수 있다.

사용자가 승인한 3번을 채택한다. 기존 분류별 기간은 공용 검색과 데이터베이스가 모두 실패했을 때만 사용하는 임시 보수적 fallback이며 공용 기준으로 저장하지 않는다.

## 재고명 정규화와 조회 키

- OpenAI 비전 구조화 결과의 `foodName`은 상품명이 아니라 식재료·식품의 대표 한국어 명칭으로 반환한다. `햇감자`, `맛있는 감자 1kg`은 모두 `감자`가 된다.
- 서버는 대표 명칭을 NFKC 정규화하고 공백·기호를 제거한 `canonical_key`를 만든다.
- 공용 기준의 실제 조회 키는 `canonical_key + storage_method + package_state`다. 같은 두부라도 냉장·미개봉과 냉동·개봉 상태는 서로 다른 기준이다.
- 구매내역에서 보관 상태가 확인되지 않으면 상품 유형에 맞는 일반적인 미개봉 보관 상태를 내부 가정으로 사용한다. 사용자가 보는 날짜는 항상 `권장 소진일(추정)`이며 제품 포장의 공식 소비기한으로 표현하지 않는다.
- OCR에 공식 표시일이 존재하거나 사용자가 날짜를 수정한 경우 공용 추정값보다 우선한다.

## 공용 권장 소진일 데이터

`public.shelf_life_rules`를 다음 책임으로 추가한다.

| 필드 | 용도 |
| --- | --- |
| `canonical_key`, `canonical_name` | 정규화된 재고 식별자와 표시명 |
| `storage_method` | `room_temperature`, `refrigerated`, `frozen` |
| `package_state` | `unopened`, `opened`, `unpackaged` |
| `duration_days` | 구매일로부터 적용할 보수적인 일수 |
| `source_title`, `source_url` | 검색 근거 |
| `source_checked_at` | 근거 확인 시각 |
| `evidence_type` | `curated` 또는 `ai_sourced` |
| `confidence` | 0~1 구조화 신뢰도 |
| `status` | `active`, `rejected` |
| `created_at`, `updated_at` | 변경 추적 |

동일 조회 키에는 하나의 활성 규칙만 둔다. 인증 사용자는 `active` 규칙만 읽을 수 있고 클라이언트에서 쓰거나 삭제할 수 없다. 검색 결과 저장은 service-role 권한을 가진 Edge Function만 수행한다. `duration_days`는 1~3650, 출처는 HTTPS URL, 명칭과 보관 조건은 허용값이어야 한다.

활성 규칙이 없거나 `source_checked_at`이 365일보다 오래되었으면 cache miss로 처리한다. 오래된 규칙은 검색 성공 전까지 fallback으로 사용할 수 있지만 새 검색 결과가 검증되면 교체한다.

## 검색과 캐시 흐름

1. `purchase-ocr`가 각 이미지에서 텍스트와 상품 후보를 추출한다.
2. 서버가 식품 후보를 대표 재고명과 보관 조건으로 정규화한다.
3. 모든 고유 조회 키를 한 번에 `shelf_life_rules`에서 조회한다.
4. cache miss만 모아 OpenAI Responses API의 웹 검색으로 조사한다. 정부·공공 식품안전 자료와 제조사 안내를 우선하고, 찾은 기간 범위에서는 짧은 값을 선택한다.
5. 결과를 strict schema와 결정적 범위 검사로 검증한다. 유효한 결과만 공용 DB에 저장한다.
6. 검색 실패 또는 근거 부족 항목은 분류별 보수적 fallback 날짜를 적용하고 `확인 필요`로 반환한다. 이 fallback은 공용 DB에 저장하지 않는다.
7. 클라이언트에는 계산된 날짜, 검수 필요 여부와 내부 비고를 반환한다. 원본 이미지와 전체 OCR 텍스트는 서버에 저장하지 않는다.

한 요청에서 여러 cache miss가 발생하면 하나의 제한된 검색 요청으로 묶는다. 검색 결과에는 품목별 출처가 반드시 있어야 하며, 출처 없는 값은 저장하지 않는다.

## 다중 이미지 선택과 분석

- 기존 R1~R5 샘플은 탭 즉시 분석하지 않고 선택·선택 해제만 한다.
- 샘플 목록 아래, `닫기` 위에 `이미지 등록` 버튼을 둔다.
- `이미지 등록`은 웹에서 파일 탐색기, Android에서 사진 보관함을 연다.
- JPEG·PNG·WebP 이미지를 한 번에 최대 10장까지 선택한다. 각 파일은 5MB 이하여야 한다.
- 샘플과 사용자 이미지 모두 같은 선택 목록과 같은 서버 분석 경로를 사용한다.
- 선택된 이미지가 있으면 `선택한 이미지 분석` 버튼을 활성화한다.
- 이미지는 한 장씩 순차 분석하고 처리 직후 data URL을 해제해 Android 메모리 사용을 제한한다.
- 하루 OCR 한도는 이미지 한 장당 1회로 계산한다. 한 번에 4장을 분석하면 4회를 소비한다.
- 일부 이미지 분석이 실패해도 성공한 결과는 보존한다. 실패한 이미지는 파일명과 재시도 버튼만 표시하며 다른 품목의 편집값을 초기화하지 않는다.
- 서로 다른 이미지에서 상품명·수량·단위가 완전히 같은 행이 발견되면 자동 삭제하지 않고 중복 가능 항목으로 `확인 필요` 처리한다.

## 검수 팝업

분석이 끝나면 이미지 원문 전사와 판정 배지를 노출하던 현재 결과 화면을 편집 가능한 검수 화면으로 교체한다.

- 사용자에게 노출하는 열은 `재고명`, `수량`, `권장 소진일` 세 가지다.
- `수량`은 `300g`, `2개`, `500ml`처럼 값과 단위를 함께 편집하는 입력란이다.
- `권장 소진일`은 `YYYY-MM-DD` 입력란이며 공용 기준으로 계산된 추정값을 기본으로 넣는다.
- `확인 필요` 식품을 목록 위로 올리고 빨간 테두리를 적용한다.
- 하나라도 확인 필요 항목이 있으면 최상단에 `직접 입력해야 하는 항목들이 있습니다.`를 빨간 경고 문구로 표시한다.
- 사용자가 확인 필요 행을 수정해 세 필드가 모두 유효해지면 강조를 해제한다. 값을 바꾸지 않았더라도 최종 `등록` 버튼은 완전한 세 필드를 사용자가 승인한 것으로 간주한다.
- 비식품 후보는 등록 목록에 포함하지 않는다. 원본 OCR, 비식품 판정과 제외 비고는 등록 완료 또는 취소 시 폐기한다.
- 검수 목록은 세로 스크롤되며 스크롤 바를 숨긴다. 하단의 `등록`과 `다른 이미지 선택` 버튼은 접근 가능한 크기를 유지한다.
- `등록`을 누르면 전체 행을 다시 검증한다. 빈 재고명, 지원하지 않는 수량 단위, 잘못된 날짜 또는 이미 지난 추정일이 있으면 DB를 변경하지 않고 해당 행을 강조한다.
- 등록 성공 후에만 재고 화면으로 이동한다.

## 내부 판정 데이터

`inventory_lots`에는 최종 등록된 행에 한해 다음 메타데이터를 추가한다.

- `import_resolution`: `auto`, `user_confirmed`, `user_edited`
- `internal_note`: 수량 미확인, 낮은 신뢰도, 공용 기준 fallback, 중복 가능처럼 개인정보가 없는 짧은 판정 사유

두 필드는 재고 UI에 표시하지 않고 사용자 소유 RLS 안에서만 보존한다. 주문번호, 주소, 결제정보, 전체 OCR 원문, 이미지 파일명과 이미지 자체는 저장하지 않는다. 비식품과 최종 등록되지 않은 행도 저장하지 않는다.

## 오류와 동시성

- 최종 등록은 한 번의 서버 RPC로 처리하고 idempotency key를 사용해 중복 탭·재시도로 같은 lot이 두 번 생성되지 않게 한다.
- 공용 규칙 생성은 조회 키 unique constraint와 upsert를 사용해 여러 사용자가 동시에 같은 품목을 검색해도 한 행만 활성화한다.
- 공용 검색 실패는 재고 등록 전체 실패가 아니다. fallback 날짜와 확인 필요 상태로 사용자가 계속 진행할 수 있다.
- 인증 만료, 일일 한도 초과, 파일 형식·크기 오류는 이미지별로 구분해 안내한다.

## 구현 경계

- 이미지 선택: Expo ImagePicker의 웹·Android 공통 API
- OCR·권장 소진일 해석: 인증된 Supabase Edge Function과 OpenAI Responses API
- 공용 기준 저장과 최종 등록: Supabase Postgres, RLS, security-definer RPC
- 클라이언트 상태: 선택 이미지, 이미지별 처리 상태, 편집 가능한 검수 행
- 기존 홈·재고의 등록 진입점과 시각 스타일은 유지하고 결과 단계만 확장한다.

## 테스트와 완료 기준

- 정규화된 같은 재고명이 동일 cache key를 사용한다.
- 활성 cache hit에서는 웹 검색 호출이 발생하지 않는다.
- cache miss만 검색되고 유효한 근거가 공용 DB에 한 번 저장된다.
- 검색 실패 시 fallback이 확인 필요로 반환되고 공용 DB에는 저장되지 않는다.
- 확인 필요 항목 정렬, 수량 문자열 파싱, 날짜 검증, 사용자 수정 상태 전환을 단위 테스트한다.
- 여러 이미지 중 일부 실패 시 성공 결과와 기존 편집값이 유지된다.
- 최종 등록 전에는 재고 DB가 바뀌지 않고, 등록 RPC 재시도도 중복 lot을 만들지 않는다.
- 웹 파일 탐색기와 Android 사진 보관함에서 다중 선택이 가능하다.
- 전체 테스트, TypeScript 검사, Expo 웹 production export와 실제 브라우저 검수를 통과한다.
