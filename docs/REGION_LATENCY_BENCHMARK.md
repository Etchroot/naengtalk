# 서울·싱가포르 DB 왕복 측정

측정일: 2026-10-13 15:47 KST부터. 사용자 요청으로 실기기 없이 서버 측 지연을 비교했다.

## 실행 환경과 방법

- 싱가포르: 냉톡 기존 프로젝트. 서울: 사용자 승인으로 ImaginArena 기존 프로젝트 사용.
- 서울 별도 프로젝트 생성은 무료 활성 프로젝트 제한으로 거절됨. 새 프로젝트 생성·요금제 변경 없음.
- 각 프로젝트에 동일한 합성 데이터 40행과 임시 RPC·Edge 함수만 추가. 기존 서비스 테이블·사용자 데이터는 조회하거나 변경하지 않았다.
- Edge 실행 지역 × DB 지역 네 조합, 1·4·8회 순차 왕복을 섞어서 각 조합/프로필 30회 측정. 첫 호출 4회와 준비 12회는 통계에서 제외. 추가로 네 조합마다 4개 동시 요청을 3묶음(12회) 수행.
- 총 424회 함수 호출, 혼합 측정 360회, 동시 측정 48회. 전 요청 HTTP 200, 반환된 실행 지역 및 헤더 일치, 오류 0건. 응답 크기도 동일 연산에서 모두 일치.
- `serverMs`는 함수 내부 RPC 전송부터 응답 본문 수신까지의 순차 누적 시간. AI 호출·로컬 PC에서 함수까지의 시간은 포함하지 않는다.
- 양쪽 Postgres 17.6, shared_buffers 224 MiB, effective_cache_size 384 MiB, max_connections 60 동일. 실제 컴퓨트 하드웨어·백그라운드 부하는 완전히 통제하지 못했다.

## 서울 함수 기준 비교

단위 ms. 중앙값은 P50, P95는 95% 지점의 요청 시간이다. 소표본 통계이며 미래 지연 상한을 뜻하지 않는다.

| 순차 왕복 | 싱가포르 DB P50 / P95 | 서울 DB P50 / P95 | P50 차이 |
| --- | ---: | ---: | ---: |
| 1회: 재고 조회 크기 | 122 / 257 | 54 / 124 | 68 |
| 4회: OCR의 DB 관련 경로 대체 | 433 / 583 | 128 / 175 | 305 |
| 8회: 메뉴 상담 최대 DB 관련 경로 대체 | 840 / 1,054 | 250 / 299 | 590 |

8회 경로는 서울 DB에서 중앙값 약 70% 감소. 로컬 실행기에서 함수 응답까지 포함한 같은 경로 중앙값은 919ms → 344ms였다. 로컬 네트워크 경로를 모든 사용자에게 일반화하지 않는다.

## 함수 지역도 함께 바꿨을 때: 8회 경로

| 함수 실행 지역 | DB 지역 | P50 | P95 | 4개 동시 요청 P50 / P95 |
| --- | --- | ---: | ---: | ---: |
| 서울 | 싱가포르 | 840 | 1,054 | 753 / 1,133 |
| 서울 | 서울 | 250 | 299 | 237 / 432 |
| 싱가포르 | 싱가포르 | 465 | 684 | 351 / 734 |
| 싱가포르 | 서울 | 1,504 | 2,152 | 1,392 / 2,284 |

이 표의 네 조건은 실제 호출이며 같은 함수에서 순차 왕복을 실행했다. 거리만으로 대칭적인 지연을 가정하지 않는다. 양쪽 방향의 라우팅·프로젝트 부하·서버 차이를 분리 측정한 실험은 아니다.

## 코드에서 확인한 최대 왕복과 한계

현재 작업 트리의 메뉴 상담은 인증 1 + 사용 제한 1 + 재고 1 + 공개/공유 후보 검색 2 + 첫/재작성 후보 상세 2 + 관측 기록 1 = 최대 8회 서버 왕복이다. 관측 기록도 응답 전에 기다리므로 포함했다. 여기서 인증 외 7회가 DB 관련 요청이다. AI 분류·생성·재작성 최대 3회는 별도다.

OCR/직접 텍스트 분석 함수는 인증·사용 제한·캐시 읽기·캐시 쓰기 최대 4회다. 상품 40개라도 캐시 DB 읽기/쓰기는 각각 묶음 1회다. 여러 사진 처리·채팅 재고 등록 전체 흐름은 여러 함수 호출을 합치므로 단일 함수 최대치와 다르다.

본 측정은 동일 합성 SQL/RPC로 인증 응답 크기·조회 응답 크기·작은 쓰기·왕복 수를 재현했다. 실제 Auth, rate limit, 관측 집계, 앱 SQL/RLS, OpenAI 처리 시간을 그대로 실행한 전체 기능 시험이 아니다. 현재 코드의 미배포 변경도 있으므로 실제 운영 요청에 항상 8회가 발생한다고 단정하지 않는다.

## 판단

- 한국 중심 서비스에서는 서울 함수 + 서울 DB가 이번 시험에서 가장 빨랐다. DB 관련 순차 8회에 약 0.59초의 중앙값 차이를 확인했다.
- 여러 초가 걸리는 AI 응답의 전체 지연이 이 비율만큼 줄어든다는 뜻은 아니다. AI 모델·외부 검색 지연은 남는다.
- DB를 옮기기 전, DB 왕복이 많은 함수만 싱가포르 DB와 같은 지역에서 실행하도록 비교하는 대안이 있다. 이번 시험에서 서울 함수→싱가포르 DB보다 서버 내부 중앙값이 375ms 감소했지만, 클라이언트→함수 지연도 함께 고려해야 한다. 운영 설정은 아직 변경하지 않았다.
- DB 이전은 별도 작업이다. 실제 서비스 데이터·Auth·Storage·함수·환경변수·OAuth 복귀 경로를 포함해 이전 계획이 필요하다.

## 정리 확인

두 프로젝트의 임시 Edge 함수 `region-bench-20261013`, 공개 RPC `bench_region_20261013(text)`, 합성 테이블 2개와 전용 스키마 `bench_region_20261013`을 삭제했다. 실제 재조회 결과 양쪽 모두 스키마/RPC null, 남은 테이블 false, 배포 함수 0건.

공급자의 실행/접속 로그와 CLI의 표준 로그인 역할 관리 흔적은 정리 대상 합성 DB 데이터와 다르며 삭제했다고 주장하지 않는다. 로컬 측정 결과에는 키나 기존 앱 사용자 데이터가 없다.
