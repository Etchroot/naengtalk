# 냉톡 상세 작업 방식

이 문서는 특정 작업에서만 읽는 상세 절차다. 모든 작업 시작 시 자동으로 읽지 않는다.

## 기획과 개발 전환

- 사용자가 명시적으로 기획 완료와 개발 시작을 선언하기 전에는 앱 코드, 인프라, 데이터베이스 migration 또는 배포 작업을 시작하지 않는다.
- 그전까지는 문제 정의, 사용자 흐름, 기능 범위, 데이터·AI 구조, 화면 설계, 테스트 기준과 제출 전략을 구체화한다.
- 개발 전환 후에도 큰 범위 변경이나 제품 판단이 필요하면 사용자와 다시 합의한다.

## Product Design 플러그인

- 실제 앱 UI/UX 디자인 단계에서는 설치된 Product Design 플러그인을 사용한다.
- `product-design:index`를 먼저 읽고 목적에 맞는 하위 스킬을 선택한다.
  - 시각 방향과 대안 탐색: `product-design:ideate`
  - 승인된 이미지·목업 구현: `product-design:image-to-code`
  - 구현 화면과 사용자 흐름 검수: `product-design:audit`
- 생성된 대안을 임의로 확정하지 않고 사용자가 승인한 디자인만 구현 기준으로 삼는다.
- 와이어프레임·디자인 결정·접근성 검수 결과는 `docs/PRD.md`와 `TODO.md`에 연결한다.

## 문서 관리

- `docs/PRODUCT_PLAN.md`: 문제, 타깃, 차별점, MVP와 사업·제품 위험
- `docs/PRD.md`: 사용자 흐름, 기능 요구사항, 제품 규칙과 수용 기준
- `docs/TRD.md`: 기술 구조, 데이터, AI 경계, 보안, 테스트와 배포
- `docs/PRODUCT_DECISIONS.md`: 여러 기능에 걸쳐 이미 확정된 제품 결정의 보존 기록
- `TODO.md`: 완료 조건, 담당, 상태와 차단 요소
- `HUMAN-IN-THE-ROOF.md`: 사용자가 내린 결정과 결과에 미친 영향
- `SUBMISSION.md`: 구현·배포로 검증된 사실만 입력하는 제출 템플릿
- 기존 분류에 맞지 않는 새 주제는 `docs/<TOPIC>.md`로 분리하고 `AGENTS.md`에는 상세 대신 발견용 경로만 추가한다.
- 문서와 실제 동작이 충돌하면 동작을 검증한 뒤 문서를 고친다. 제품 의도 변경이 필요하면 사용자 승인을 먼저 받는다.

## 제출 작업

- 심사 기간 동안 정상 접속 가능한 배포 서비스 링크를 제공한다.
- `SUBMISSION.md`에는 해결 문제, AI 활용 방식, 실제 사용한 AI 도구, 웹 링크와 Android 설치 안내를 포함한다.
- 실제 구현·배포에서 검증되지 않은 AI 도구나 기능은 제출 문서에 기재하지 않는다.
- 제출 직전 `docs/HACKATHON_RULES.md`의 일정과 형식을 공식 페이지에서 다시 확인한다.

## 보안과 개인정보

- API 키와 service role은 서버 비밀값으로만 관리한다.
- OpenAI API 키는 실제 연동 단계에서 사용자가 등록하며, 그전에는 실제 값을 요구하거나 예제·문서에 기록하지 않는다.
- AI가 DB를 직접 수정하지 않게 하고 검증된 서버 명령과 트랜잭션으로만 재고를 변경한다.
- 구매내역 개인정보 처리 기준은 `docs/PRD.md`와 `docs/TRD.md`의 캡처·보안 구간을 따른다.
- AI 추정값은 확정 정보처럼 표시하지 않고 출처, 신뢰도 또는 `추정` 상태를 노출한다.

## 품질 확인

- 완료 보고 전에 대상에 맞는 테스트·빌드·화면·배포 검증을 실제로 실행한다.
- 검증하지 않은 결과를 완료로 표현하지 않는다.
- 중요한 구현 결과와 검증 상태는 관련 문서 및 `TODO.md`에 반영한다.
