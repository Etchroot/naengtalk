# 냉톡 PRD

- 문서 상태: 구현 기준 정리
- 기준일: 2026-09-27
- 제품명: 냉톡
- 대상 릴리스: Wanted AI Championship 2026 MVP

## 1. 제품 정의

냉톡은 1인 가구가 냉장고 재고를 대화로 확인·수정하고, 보유 재료와 권장 소진일을 고려한 맞춤 레시피를 받아 음식 낭비를 줄이도록 돕는 Android·웹 서비스다.

## 2. 목표와 비목표

### 목표

- 사용자가 재고 목록을 먼저 보지 않고도 대화로 메뉴를 결정한다.
- 구매내역 등록과 요리 완료를 재고 변화에 연결한다.
- 임박 재료를 우선 활용하되 사용자의 먹고 싶은 메뉴를 최우선 맥락으로 유지한다.
- AI의 추정과 데이터 변경을 사용자가 이해하고 통제한다.
- 심사위원이 로그인 부담 없이 핵심 흐름을 끝까지 체험한다.
- MVP의 Android·웹 구매내역 인식은 동일한 OpenAI 비전 경로를 사용하고, AI가 잘하는 글자 인식·언어 이해와 코드로 통제할 수량·날짜·안전을 분리한다.
- MVP의 생성형 AI 기능은 OpenAI GPT와 Responses API만 사용하고, 다른 생성형 AI 제공자에 의존하지 않는다.
- 단순 구조화·일반 대화는 `gpt-5.6-luna`, 복잡한 레시피 재설계·검색 근거 판단은 `gpt-5.6-terra`로 분리하고, Luna 결과의 신뢰도가 낮을 때만 요청당 한 번 Terra로 승격한다.

### 비목표

- 모든 형태의 영수증과 식재료 사진을 완전 자동 인식하지 않는다.
- 모든 요리에 대해 원본 레시피 없이 완전히 새로운 조리법을 생성하지 않는다.
- 식품 안전 또는 영양에 대한 전문적 보증을 제공하지 않는다.
- 사용자의 확인 없이 여러 재료를 차감하지 않는다.

## 4. 기능 요구사항

### FR-1. 인증과 체험

- 저장된 유효 세션이 없는 첫 실행에는 홈 대신 전용 로그인 화면을 표시한다.
- 로그인 화면 중앙에는 `게스트 로그인(심사)`과 `Google 로그인` 버튼 두 개를 명확히 구분해 제공한다.
- `게스트 로그인(심사)`을 누르면 Supabase 익명 인증과 게스트 시드 초기화를 완료한 뒤 홈으로 이동한다. 초기화 중에는 중복 클릭을 막고 진행 상태를 표시하며 실패하면 로그인 화면에서 재시도할 수 있다.
- `Google 로그인`은 production OAuth 설정 후 사용자 프로필과 pantry를 준비해 홈으로 이동할 예정이다. 현재 버튼은 미연결 상태를 명확히 안내하고 로그인 화면을 유지한다.
- 현재 심사용 경로는 게스트 익명 인증이며 일반 사용자 Google 로그인은 출시 전 남은 작업이다.
- 심사위원은 게스트로 진입할 수 있다.
- Google 인증 또는 게스트 초기화가 성공하면 별도의 온보딩, 초기 설정 체크리스트나 `냉톡 시작하기` 단계를 표시하지 않고 바로 홈으로 이동한다. 일반 사용자는 알레르기·조리도구·재고를 각 기능 화면에서 필요할 때 등록한다.
- Android와 웹은 Supabase 세션을 플랫폼에 맞는 안전한 저장소에 유지한다. 앱·웹 재실행 시 인증 가드가 세션 복원과 토큰 갱신을 먼저 확인하고, 유효하면 로그인 화면을 건너뛰어 홈으로 이동한다.
- 설정에는 `로그아웃`을 제공한다. 로그아웃하면 로컬 세션을 삭제하고 로그인 화면으로 이동하되 서버의 일반 사용자 데이터는 삭제하지 않는다.
- 게스트가 로그아웃한 뒤 다시 게스트로 진입하면 새 익명 사용자와 새 시드가 생성된다. 이전 게스트 데이터는 즉시 재연결하지 않고 기존 7일 비활성 정리 정책에 따라 삭제한다.
- 토큰 갱신 실패, 계정 폐기 또는 7일 비활성 정리로 게스트가 삭제된 경우에는 저장 세션이 있더라도 로그인 화면으로 돌아간다.
- 게스트마다 기준 샘플에서 복제된 독립 데이터 공간을 제공한다.
- 게스트 데이터는 다른 세션과 공유되지 않는다.
- 게스트 챗봇은 김치 두부찌개 같은 고정 응답만 반환하지 않고 일반 사용자와 동일한 AI 대화·검색·레시피 재설계 파이프라인을 사용한다.
- 게스트는 심사위원의 후속 채팅을 계속 처리하며, 맛·시간·재료 요청이 바뀌면 최신 재고를 기준으로 제안을 다시 계산한다.
- 게스트가 `요리 완료`를 확정하면 일반 사용자와 동일한 검증·미리보기·트랜잭션을 거쳐 해당 게스트 pantry의 재고를 실제 차감한다.
- 새 게스트 pantry에는 한식에 흔히 쓰는 재료·조미료 총 30종과 기본 조리도구 16종, `새우` 알레르기를 제공한다. 식품 재고는 게스트별 Supabase DB에, 조리도구 기본 목록은 앱 상태에 보관한다.
- 주요 조미료인 간장·설탕·소금·된장·고추장은 고체 500g, 액체 500ml로 넉넉히 제공한다. 소금의 심사용 권장 소진일만 `2127-03-20`으로 고정하고, 나머지 품목은 `docs/TRD.md`의 게스트 시드 v2 상대 날짜를 따른다.
- 기본 조리도구는 가스레인지, 프라이팬, 집게, 뒤집개, 1L·2.5L·4L 냄비 등을 포함한 16종이다.
- 기존 게스트가 직접 수정한 재고·조리도구를 자동 덮어쓰지 않는다. `샘플 데이터 초기화`를 선택한 경우에만 새 시드를 적용한다.
- 게스트 초기화 기능은 해당 세션의 pantry·대화·완료 레시피만 새로운 샘플 데이터로 다시 만든다.
- `게스트로 시작`을 누를 때 공용 계정이 아니라 접속자별 Supabase 익명 사용자를 생성한다.
- 시드 복제는 사용자 ID와 시드 버전을 idempotency key로 사용해 한 번만 완료하며, 동시에 요청돼도 중복 lot을 만들지 않는다.
- 새로고침과 같은 브라우저 재접속은 저장된 익명 세션을 유지하고, 다른 브라우저·시크릿 창은 별도 게스트로 취급한다.
- 마지막 활동 후 7일이 지난 게스트의 pantry·대화·레시피·재고 이벤트와 익명 인증 사용자를 예약 작업으로 삭제한다.
- 익명 가입에는 CAPTCHA를 적용하고, 게스트별·IP별 AI 및 초기화 호출 제한을 둔다.

### FR-2. 구매내역 등록

- 우선 지원하는 주문내역 형식은 `배달의민족 장보기`, `쿠팡`, `마켓컬리`다.
- 쇼핑몰과 무관하게 종이 영수증과 같은 텍스트 행 구조를 가진 전자영수증 캡처도 범용 형식으로 지원한다. 이마트 전자영수증이 대표 예시다.
- 사용자는 지원 형식의 구매내역 또는 전자영수증 캡처를 한 번에 최대 10장까지 선택할 수 있다. 웹은 파일 탐색기, Android는 사진 보관함을 사용한다.
- MVP는 Android와 웹 모두 인증된 Supabase `purchase-ocr` Edge Function을 통해 OpenAI 비전으로 글자를 읽고 상품을 구조화한다.
- 심사용 게스트 흐름에서는 번들된 R1·R3·R4·R5를 화면에 `예시 1`~`예시 4`로 표시해 복수 선택하거나 `이미지 등록`으로 사용자 이미지를 추가할 수 있다. R2는 선택 목록에서 제외하며 샘플과 사용자 이미지는 같은 AI 분석·검수·재고 등록 서버 경로를 사용한다.
- 원본 이미지는 요청 본문으로만 전달하고 Supabase Storage·데이터베이스·애플리케이션 로그에 저장하지 않는다. 함수 메모리에서 분석을 마치면 즉시 폐기한다.
- OCR 원문과 구조화 검수 초안은 서버 데이터베이스에 영구 저장하지 않는다. 현재 등록 흐름에서만 사용하고 사용자가 등록을 확정하거나 취소하면 폐기한다.
- 등록 확정 후에는 재고 lot, 입력 방식, 지원처 유형과 구매일처럼 기능에 필요한 최소 구조화 정보만 보존한다. 주문번호·주소·연락처·결제정보와 원본 캡처는 재고 기록에 포함하지 않는다.
- 상품 썸네일의 외형은 상품 판별 근거로 사용하지 않는다. OpenAI 비전에는 화면에 보이는 상품명·수량·가격 등 텍스트만 전사하고 구조화하도록 지시한다.
- AI는 상품명, 옵션, 수량, 단위 용량, 총용량, 구매일 후보를 구조화한다.
- 구매내역 OCR은 이미지 한 장을 한 회로 계산해 사용자별 하루 10회로 제한하고, 각 이미지는 5MB 이하의 JPEG·PNG·WebP만 허용한다. 여러 이미지는 순차 처리해 일부 실패 시 성공 결과를 보존한다.
- 주문내역 형식은 쇼핑몰별 텍스트 파서로 우선 처리하고, 전자영수증은 품목 행·수량·단가·합계 패턴을 사용하는 범용 파서로 처리한다.
- 결과는 모든 인식 품목을 한 번에 확인할 수 있는 편집 가능한 검수 화면으로 제시한다. 사용자에게는 `재고명`, `수량`, `권장 소진일`만 보여주고 판정·비고·원문은 내부 상태로만 유지한다.
- OCR 원문에 상품명 또는 정규화 재고명의 텍스트 근거가 없는 품목은 등록 후보에서 제거하고, 같은 이미지에서 동일 상품명·재고명·수량·단위가 반복된 행은 하나로 합친다.
- 재고명·수량·근거 있는 권장 소진일 또는 사용자 확인 날짜가 모두 유효하면 수정 가능한 일반 행으로 보여준다. 근거 없는 식품군 fallback은 날짜를 자동 확정하지 않으며 빈 필드를 `확인 필요`로 강조한다.
- 사용자는 품목별로 등록 대상에서 제외하거나 필드를 직접 수정할 수 있고, 채팅에서도 같은 재고 정보를 정정할 수 있다.
- 구매목록 텍스트에 소비기한이 실제로 존재하면 공식 표시일 후보로 우선 입력한다. 표시일이 없으면 정규화 재고명·보관 방법·포장 상태로 공용 소비기한 DB를 먼저 조회하고, 유효한 항목이 없거나 365일 이상 지난 경우에만 OpenAI 웹 검색으로 보수적인 권장 소진 기간과 HTTPS 근거를 확인해 공용 DB에 저장한다.
- 원문에 `냉동`이 명시된 모든 식품은 종류와 무관하게 냉동 보관 기준을 사용한다. 정규화 재고명과 보관 상태를 분리해 같은 식품의 냉장·냉동 규칙 및 재고 lot을 구별한다.
- 미개봉 상온 즉석밥은 제조사 공식 보관기간 9개월을 근거로 하되 제조일과 유통 경과를 알 수 없는 구매내역의 한계를 반영해 등록일 D+180을 보수적 권장 소진일로 사용한다. 포장 표시일 또는 사용자 입력일이 있으면 항상 그 날짜를 우선한다.
- 계란·우유처럼 포장마다 표시일 차이가 큰 품목은 날짜 입력란을 강조한다. 사용자는 포장을 보고 입력하거나 `지금은 모르겠어요`를 선택할 수 있으며, 미입력은 등록을 막지 않는다.
- 공용 규칙이 없고 검색 근거도 검증하지 못하면 임의의 한 달짜리 날짜를 채우지 않는다. 사용자가 포장 표시·보관 상태를 확인해 날짜를 입력하도록 하고 사용자 날짜는 공용 규칙으로 저장하지 않는다.
- 구매내역 검수 안내에는 권장 소진일이 AI 예측값임을 별도 줄로 표시한다. 보관상태만 변경해도 검수창에 이미 입력된 날짜는 유지하며, 날짜 자체를 수정한 경우에만 사용자 입력 날짜로 기록한다. 보관상태를 바꾼 사용자는 기존 날짜의 적합성을 확인·수정할 수 있다.
- 필수값이 비었거나 형식이 잘못된 `확인 필요` 항목은 목록 최상단에 빨간 테두리로 배치하고 상단에 `직접 입력해야 하는 항목들이 있습니다.` 경고를 표시한다. 재고명·수량·권장 소진일은 모두 수정 가능한 입력란이며, 빨간 항목이나 이미지 분석 실패가 하나라도 남으면 등록 버튼을 비활성화한다.
- 사용자가 마지막 `재고에 등록`을 눌러 최종 확인한 항목만 한 번에 등록하며, 그 전에는 재고 DB를 변경하지 않는다.
- 일부 품목 또는 필드의 인식이 실패해도 성공한 결과와 사용자가 수정한 값은 유지하고, 실패한 부분만 `확인 필요` 상태로 남긴다.
- 사용자가 재분석을 요청해도 직접 수정한 값은 명시적으로 초기화하지 않는 한 덮어쓰지 않는다.
- 전체 OCR이 실패하면 `다른 캡처 선택`과 `직접 입력`을 제공한다.
- 직접 입력 경로를 항상 제공한다.
- 재고 페이지 상단의 `재고 등록` 버튼도 홈의 구매내역 등록과 동일한 공용 팝업을 연다.
- 공용 팝업에서 `직접 입력`을 누르면 자연어 입력 팝업을 열고 `식품의 이름과 용량, 소비기한을 적어주세요.`라는 placeholder와 `식품 등록` 버튼을 제공한다.
- 사용자는 쉼표 또는 줄바꿈으로 여러 식품을 한 번에 입력할 수 있다. AI는 항목별 식품명·원본 수량·단위·표시일 후보를 구조화한다.
- 서버는 구조화 결과를 단위·날짜 규칙으로 검증한다. 식품명이나 용량이 불확실한 항목만 사용자 확인 상태로 남기고, 날짜가 없으면 기존 기준표의 보수적인 `권장 소진일(추정)`을 적용한다.
- 검증을 통과한 항목은 한 번의 멱등성 있는 작업으로 lot과 재고 카드를 만들며, 등록 직후 전체 작업을 되돌리는 `실행 취소`를 제공한다.
- 실물 종이 영수증 사진과 식재료 실물 사진은 MVP 자동 인식 대상이 아니다.
- 업로드 후 냉톡이 원천을 자동 판별하고, 신뢰도가 낮을 때만 `배달의민족 장보기`, `쿠팡`, `마켓컬리`, `전자영수증`, `잘 모르겠어요` 중 하나를 선택하도록 요청한다.

### FR-3. 재고 관리

- 재고는 구매 단위의 lot으로 저장하고, 기본 목록에서는 같은 재료를 합산해 표시한다.
- 재고 목록은 기본적으로 남은 권장 소진일이 가까운 순서로 표시한다. 목록 상단의 정렬 버튼에서 `남은 소비기한 순` 또는 `이름순`을 선택할 수 있으며, 이름순은 한국어 사전식 순서를 따른다.
- 각 lot은 사용자가 입력하거나 구매내역에서 읽은 원본 수량·단위와, 레시피 계산에 쓰는 표준 수량·단위를 함께 보존한다.
- 표준 계산 단위는 우선 `g`, `ml`, `개`를 사용한다. 포장에 총중량·총용량이 있거나 사용자가 값을 제공한 경우에만 변환한다.
- 예를 들어 `두부 300g × 2팩`은 `2팩 · 총 600g`, `달걀 10개`는 `10개`로 표시한다.
- `1망`, `1봉`처럼 환산 근거가 없는 단위는 원본 그대로 저장하며, 평균 중량을 이용해 자동 환산하지 않는다.
- 같은 재료라도 안전하게 변환할 수 없는 단위끼리는 하나의 숫자로 합산하지 않고 각 단위의 소계를 함께 표시한다.
- 사용자는 `0.5팩`, `반 봉지`처럼 원본 단위 기준의 소수 수량을 입력할 수 있다.
- 보관 위치, 수량·단위, 구매일, 표시 소비기한 또는 권장 소진일을 수정할 수 있다.
- 농산물·육류·생선 등은 정규화된 식재료 종류, 구매일, 보관 위치와 개봉 상태에 맞는 기준표로 `권장 소진일(추정)`을 계산한다.
- 기준표는 식약처·식품안전나라의 국내 소비기한·보관 원칙을 우선 적용하고, 개별 비포장 식재료의 보관기간은 USDA FoodKeeper 공개 데이터를 보완 근거로 사용한다.
- 참고 기간이 범위로 제공되면 보수적으로 짧은 값을 적용하고, 사용자에게 적용 출처·보관 상태·계산 기준일을 확인할 수 있게 한다.
- 상품명에서 냉장·냉동 상태를 판별할 수 없으면 더 짧은 냉장 기준을 기본 적용하고 사용자가 수정할 수 있게 한다.
- 날짜가 공식 표시 정보가 아니면 `권장 소진일(추정)`으로 표시하고 계산 근거를 제공한다.
- 사용자가 개봉하거나 냉장·냉동 위치를 옮긴 사실을 채팅 또는 재고 화면에서 기록하면 해당 상태의 기준표로 다시 계산한다.
- AI는 식재료·보관 상태·개봉 상태의 분류만 담당하고 실제 날짜 산술은 결정적 규칙 코드가 수행한다.
- 채팅에서 산 식품·받은 식품·사용한 식품·현재 남은 양을 말하면 AI는 변경안만 제시한다. 단일·다중 변경 모두 재료명·수량을 편집 가능한 확인창에서 승인하기 전에는 DB를 수정하지 않는다.
- 새로 추가한 식품은 권장 소진일까지 확인·수정한 후 등록한다. 등록되지 않은 식품을 소비했다고 말하면 그 소비 항목은 차감하지 않는다.
- 현재 재고보다 많이 소비하면 품목명을 명시한 전량 소비 확인창을 띄운다. 취소 시 원안으로 돌아가고 확인 시 현재 재고량까지만 차감한다. 레시피 `요리 완료` 사용량에도 같은 확인을 적용한다.
- 차감은 권장 소진일이 가장 가까운 lot부터 적용한다.

### FR-4. 대화형 메뉴 상담

- 사용자는 메뉴명, 맛, 시간, 난이도, 조리도구 등 자유 형식으로 요청할 수 있다.
- 유효한 추천이 가능하면 기본값 `1인분`, `보유 조리도구`, `보통 난이도`를 적용해 바로 한 가지 메뉴를 제시한다.
- 챗봇은 안전, 실행 가능성 또는 재고 변경 정확도에 꼭 필요한 경우에만 한 번에 하나의 핵심 조건을 질문한다.
- 알레르기는 설정값을 자동으로 읽으며 채팅마다 반복해서 질문하지 않는다.
- 사용자가 재고를 묻거나 남은 양을 말하면 구조화된 재고 조회·변경안을 만든다.
- 재고 변경 의도가 불명확하면 확인 질문을 하고 DB를 수정하지 않는다.
- 일반 사용자의 각 메시지는 생성 시점부터 정확히 30일 동안 보관하고 이후 자동 삭제한다. 계속 대화하더라도 30일이 지난 과거 메시지의 보존 기간은 연장하지 않는다.
- 채팅 화면과 AI 대화 문맥에는 삭제되지 않은 최근 30일 메시지만 사용하며, 오래된 메시지에서 만든 요약도 원문 보존 기간을 넘어 남기지 않는다.
- 대화 기록이 만료되어도 사용자가 확정한 재고 변경 이력과 `요리 완료`로 저장된 레시피는 각 기능의 독립 기록으로 유지한다.
- 게스트 대화는 일반 사용자 30일 정책을 적용하지 않고 게스트 전체 데이터의 마지막 활동 후 7일 정리 정책을 따른다.

### FR-5. 레시피 추천

- 추천은 먹고 싶은 메뉴, 현재 재고, 권장 소진일, 조리시간, 난이도를 함께 고려한다.
- 알레르기·식품 안전, 보유 조리도구와 사용자가 명시한 조리시간은 모든 후보에 적용하는 필수 조건이다.
- 메뉴가 구체적이면 `사용자 메뉴 의도 → 조리 가능성 → 보유 재료 활용도 → 임박 재료` 순으로 우선한다.
- 메뉴가 구체적이든 막연하든 구매 필요 품목 0개를 최상위 우선순위로 한다. 같은 구매 수 안에서 임박 재료·보유 재료 활용도·메뉴 의도·조리 부담을 비교한다.
- 추천에는 `두부의 권장 소진일이 3일 남았고 추가 구매 없이 만들 수 있어요`처럼 핵심 선정 이유를 짧게 표시한다.
- 점수가 비슷해도 최상위 후보 1개만 먼저 제시하고 선정 이유를 설명한다.
- 사용자가 맛·시간·재료·메뉴에 대한 후속 요청을 보내면 기존 제안을 수정하거나 다음 순위 후보로 교체한다.
- 최근 완료한 메뉴는 반복 우선순위를 낮추되 사용자가 명시적으로 다시 요청하면 제한하지 않는다.
- 기본 레시피 후보는 사용자가 전처리한 MFDS·MAFRA 공공데이터를 저장한 Supabase `recipe_catalog`에서 먼저 찾는다.
- 공공데이터 후보가 채택 기준에 미달하면 요리 완료 후 사용자가 명시적으로 공유한 AI 생성 레시피를 2순위로 찾는다. 두 DB 모두 적합하지 않을 때만 Terra가 새 레시피를 생성하며, 외부 레시피 웹 검색은 하지 않는다.
- 구체적인 메뉴 요청은 이름과 조건을, 메뉴가 정해지지 않은 요청은 권장 소진일·남은 양·구조화 재료를 기준으로 후보를 검색한다. `ingredients_raw`는 검색에 사용하지 않는다.
- 후보는 `normalized_name`, `parent_ingredient`, `search_key`와 이름 매칭으로 재고 충당 가능량·구매 필요 품목 수를 먼저 평가한다. 명시 메뉴 이름의 일치만으로 부족한 재료가 많은 후보를 채택하지 않으며, 요청 메뉴가 구매 0개로 불가능하면 가능한 다른 메뉴를 한 가지 설명과 함께 제시한다.
- 공공·공유·Terra 경로 모두 최종 레시피의 구매 필요 품목이 1개를 넘지 않아야 한다. 가능한 구매 0개 레시피는 구매 1개 레시피보다 항상 우선한다. AI의 재고·구매 표시는 서버가 실제 lot과 비교해 재검증한다.
- 후보들이 재고 검증에서 탈락하면 부족하다고 판정된 품목을 AI에 알려 재고만으로 가능한 메뉴를 한 번 더 생성·검증한다. 그래도 실패하면 구매 제한을 풀지 않고 재료·요청 변경을 안내하는 구체적인 오류를 보여준다.
- 적합한 후보가 없거나 정확도가 임계값보다 낮으면 만개의레시피·YouTube·일반 웹을 검색하지 않는다. 이 경로에서는 Luna가 아니라 `gpt-5.6-terra`가 사용자 재고, 임박 재료, 알레르기, 조리도구, 시간과 후속 요청을 입력받아 레시피를 생성한다.
- 공공 DB 후보의 변형과 Terra 생성은 동일한 공용 레시피 지침과 결정적 안전 검증을 적용한다.
- 대체·제외한 재료, 조정한 수량·인분, 바뀐 조리도구와 단계는 안전 검증용 구조화 데이터로만 유지하고 사용자 화면에는 별도 변경점 목록을 표시하지 않는다.
- 육류·생선·달걀·해산물처럼 위해 가능성이 높은 재료의 가열·위생 단계는 결정적 안전 조건을 통과해야 한다.
- 고위험 단계 검증에 실패하면 해당 DB 후보 또는 Terra 생성 결과를 완성본으로 제시하지 않고 조건 완화나 다른 메뉴를 제안한다.
- 양념 배합, 채소 추가·제외, 인분·농도 조정처럼 위해 가능성이 낮은 변경은 안전 조건을 해치지 않는 범위에서 AI가 설계할 수 있다.
- 공공 CSV 원문과 카탈로그 전체를 클라이언트에 제공하지 않는다. 화면에는 선택·변형된 한 개 레시피에 필요한 최소 데이터만 반환한다.
- 재고만으로 가능한 경우 `현재 재료로 가능`을 명시한다.
- 사용자가 지정한 메뉴에 필수 재료가 없으면 누락 재료와 그 재료가 필수인 이유를 설명한다.
- 이때 `필수 재료 구매 후 원하는 메뉴 만들기`와 `현재 재료로 원래 맛·형태 의도를 살린 다른 메뉴 만들기`를 같은 응답에서 제시한다.
- 안전하고 메뉴의 정체성을 해치지 않는 대체재가 검증된 경우에만 세 번째 대체 선택지를 제공하고 예상 맛·조리 차이를 설명한다.
- 사용자의 요청과 다른 메뉴로 바꾸는 경우 이유와 선택지를 제시한다.
- 사용자가 분기를 선택하기 전에는 레시피 제안을 확정하거나 재고를 변경하지 않는다.

### FR-6. 레시피 상세와 조리

- 채팅 탭 진입만으로 레시피 상세를 자동 표시하지 않는다.
- 대화 속 `레시피 전체 보기`를 누르면 전체 화면 상세를 연다.
- 상세에는 제공일, 예상 시간, 인분, 재료와 사용량, 단계, 주의사항과 예상 재고 변경이 포함된다. 난이도와 참고 출처 카드는 MVP 사용자 화면에 표시하지 않는다. 설명에도 AI가 임의로 적은 외부 레시피 사이트를 출처로 표시하지 않으며, 공공 DB 후보일 때만 검증된 기관명을 붙인다.
- 실제 가열·조리 작업이 1분을 초과하는 단계에만 해당 시간의 타이머 버튼을 제공한다. 계량·재료 꺼내기·손질·담기 같은 비조리 작업과 1분 이하 작업에는 타이머를 제공하지 않는다.
- 현재 Android·웹 공용 화면은 앱 내부 타이머를 사용한다. Android 시스템 타이머 연결은 후속 범위다.
- 웹은 실제 앱 내부 타이머를 제공한다. 종료 시각 기반으로 남은 시간을 계산하고, 화면 전환 후에도 유지한다. 브라우저 종료·절전 중 알람 전달은 보장하지 않는다.
- 상세 영역은 스크롤 가능하고 스크롤 바는 숨긴다.

### FR-7. 요리 완료와 기록

- `요리 완료`를 누르면 예상 재고 차감 내역을 먼저 보여주고 모든 재료의 사용량을 숫자 입력란으로 직접 수정할 수 있게 한다. 단위는 레시피에서 검증된 단위로 고정한다.
- 레시피 생성 시 간장처럼 소량 사용하는 액체 조미료는 `T`(큰술, 15ml)와 `t`(작은술, 5ml)로 제시하고, 재고 차감 시에는 `ml`로 환산한다.
- 레시피 생성 지침은 조리도구 세척 지시와 내부 재고 차감 규칙을 설명하는 문구를 사용자용 단계에 넣지 않는다.
- 수치와 검증된 환산 근거가 있는 사용량은 차감 미리보기에 자동 포함한다.
- `약간`, `적당량`, `한 바퀴`처럼 불확실하거나 환산 근거가 없는 사용량은 자동 차감하지 않고 확인 필요 상태로 표시해 사용자가 수량을 입력하거나 제외할 수 있게 한다.
- 레시피 조리를 시작하면 임시 조리 세션을 생성하고 기본 예상 사용량을 복제한다.
- 조리 중 사용자가 재료를 추가·감소·취소했다고 말하면 임시 사용량 원장만 갱신하며 실제 재고는 변경하지 않는다.
- 사용자가 확정하면 하나의 트랜잭션으로 재고를 차감한다.
- 확정된 레시피만 제공일과 함께 레시피 탭에 저장한다.
- 저장된 레시피 카드를 누르면 전체 상세를 다시 연다.
- 저장된 상세 하단에는 `레시피 목록으로 돌아가기`와 `요리 완료`를 함께 제공한다. 재조리는 매번 새 조리 세션을 생성하고 현재 재고·알레르기·도구를 재검증한 뒤 차감 미리보기를 거쳐 재고를 차감한다. 같은 완료 요청의 중복 실행은 차단한다.
- AI가 새로 생성한 레시피에는 빈 따봉을 표시한다. 누르면 `좋아요 표시를 하면 이 레시피가 다른 사용자도 이용할 수 있도록 공유됩니다.` 안내와 취소·확인 버튼을 보여준다. 완료 전 확인은 공유 의사만 임시 보관하며 요리 완료 없이는 개인·공유 레시피 DB에 저장하지 않는다. 완료 성공 시 노란 따봉과 함께 개인 기록·독립 공유 사본이 생성된다. 이미 완료된 개인 AI 레시피는 나중에 공유할 수 있으며, 개인 기록을 삭제해도 공유 사본은 유지한다.
- 카드의 레시피명과 제공일은 간격을 둔 별도 행으로 표시한다. 최초 제공일은 재조리 시 덮어쓰지 않는다. `냉장고 재료 100% 활용` 문구는 표시하지 않는다.
- 차감 실패 시 레시피 완료와 재고 변경을 부분 성공으로 남기지 않는다.
- 완료 전 조리 세션의 변경은 재고 조회 결과에 확정 재고로 노출하지 않는다.
- 앱 재진입 시 조리 세션을 12시간 복구하는 흐름은 후속 범위다. 현재는 레시피 상세의 사용량 검수와 요리 완료 트랜잭션만 완료 기능으로 본다.
- 후속 구현에서도 미완료·취소·만료 세션은 실제 재고에 반영하지 않는다.

### FR-8. 임박 알림 (후속 범위)

- 기본 임박 기준은 권장 소진일 또는 소비기한 7일 이내다.
- 사용자는 알림을 끄거나 기준 일수를 변경할 수 있다.
- Android는 시스템 알림, 웹은 앱 내 배너를 제공한다.
- 기본 발송 시점은 D-7·D-3·D-1이며, 해당 시점에도 재고에 남아 있는 품목만 대상으로 한다.
- 같은 날 여러 품목이 대상이면 `두부 외 3개 재료가 곧 권장 소진일이에요`처럼 하나의 알림으로 묶는다.
- 사용자별 시스템 알림은 하루 최대 한 번만 발송한다.
- 기본 발송 시간은 사용자 현지 시간 오후 6시이며 설정 화면에서 변경할 수 있다.
- 사용자 시간대가 변경되면 다음 예약부터 새 시간대의 설정 시각을 적용하고 같은 현지 날짜의 중복 알림은 보내지 않는다.
- 알림을 누르면 발송 당시 lot ID를 기준으로 현재 남은 재고와 권장 소진일을 다시 검증한 뒤 채팅 화면을 연다.
- 채팅 첫 메시지는 현재도 임박한 재료를 알려주고 `어떤 메뉴가 당기세요?`처럼 메뉴·맛·시간 입력을 유도한다.
- 발송 후 이미 사용·폐기되어 대상이 없으면 일반 채팅 화면을 열고 알림 대상이 더 이상 남아 있지 않음을 안내한다.
- 알림에서 해당 재료를 활용한 메뉴 상담으로 진입할 수 있다.

### FR-9. 탐색과 화면

- 홈 콘텐츠는 높이를 2:1로 나눠 상단 2/3에 권장 소진일이 가장 가까운 재료 몇 가지를 보여주고, 하단 1/3을 좌우로 나눠 구매내역 등록과 챗봇 진입을 배치한다. 화면이 작아져도 홈 구조를 재배치하거나 스크롤로 핵심 영역을 숨기지 않고, 기준 360×800 캔버스의 헤더·텍스트·아이콘·카드·여백·하단 내비게이션을 같은 비율로 축소해 한 화면에 모두 표시한다.
- 홈 제목 왼쪽에는 다른 화면의 홈 버튼과 같은 크기·모양의 영역을 두고 정식 냉톡 앱 아이콘을 표시한다.
- 홈의 임박 재료 행은 `재료명 → 남은 수량 → 권장 소진일` 순서로 표시하고 권장 소진일을 굵게 강조한다. 카드 상단 오른쪽에는 기기의 현지 날짜를 `Today`와 `MM.DD` 두 줄로 표시해 날짜를 바로 비교할 수 있게 한다. 현지 오늘보다 권장 소진일이 앞선 재고의 날짜는 홈과 재고 목록에서 빨간색으로 표시하고, 오늘 날짜는 경과로 처리하지 않는다.
- 홈의 임박 재료는 작은 화면에서 4개를 기본 표시하고, 앱 프레임의 세로 공간이 확보되면 5개 또는 최대 6개까지 자동으로 늘린다. 추가 표시 때문에 하단 행동 카드나 내비게이션이 겹치면 안 된다.
- 홈 하단 행동 카드의 제목은 `구매내역 등록`, `오늘 뭐 먹지?`로 표시한다. 두 제목은 기기별 카드 폭에 맞춰 16px·17px·19px로 반응형 조절하되 줄바꿈 없이 한 줄을 유지한다.
- 홈의 임박 재료 카드와 두 행동 카드는 하나의 냉장고를 이루는 문·서랍처럼 보여야 한다. 선 형태의 부분 광택 대신 각 카드 테두리 안쪽 전체에 동일한 흰색 림을 두고, 바깥 우하단 그림자로 반들반들하게 돌출된 냉장고 도어의 깊이를 표현한다. 큰 상단 카드는 연녹색, 구매 등록은 연베이지, 메뉴 상담은 글자 대비를 지키는 비스포크 계열의 밝은 새틴 하늘색을 사용한다. 큰 상단 카드의 하단 중앙과 두 행동 카드의 상단 중앙에는 실제 냉장고처럼 오목한 가로 손잡이 음영을 배치한다. 위에서 아래로 잡아 여는 두 행동 카드의 손잡이는 상단 카드 손잡이와 상하 방향을 반대로 표시한다. 행동 카드는 누를 때 우하단으로 짧게 내려가며 그림자가 줄어드는 촉각 피드백을 제공하되 텍스트 대비와 2:1 배치를 해치지 않는다.
- 모든 주요 섹션의 제목 상단바는 컴팩트 높이와 구분선을 유지한다. 홈은 크게 강조한 `냉톡` 오른쪽에 `오늘도 남김없이, 나만의 한 끼`를 한 줄로 배치하고, 다른 섹션은 의미가 중복되는 부제를 제거해 큰 제목만 표시한다. 상단바 아래 첫 오브젝트와의 기준 간격은 채팅 화면의 첫 안내 카드 간격과 동일하게 16px로 통일하고, 전역 캔버스 축소 시 같은 비율로 줄인다.
- 웹에서는 앱 본문을 일반 Android 휴대전화에 가까운 9:20 비율로 표시하고, 브라우저 높이를 거의 채우되 주변 영역은 여백으로 남긴다. 앱 바깥에는 진한 베젤, 둥근 모서리와 그림자를 웹에서만 적용해 실제 휴대폰 화면처럼 구분한다.
- 모바일 웹 채팅 입력에 소프트 키보드가 표시돼 가시 영역 높이가 줄어도 9:20 앱 프레임 자체를 축소하지 않는다. 프레임을 위로 이동해 채팅 입력창과 전송 버튼이 키보드 바로 위에 남도록 하며, 이때 상단 채팅 내역이 화면 밖으로 가려지는 것은 허용한다.
- 채팅 입력창과 전송 버튼은 좁은 모바일 폭에서도 동일 행 안에서 프레임의 안쪽 여백을 유지하고 베젤을 넘어가지 않아야 한다.
- 주요 실행 버튼의 라벨(`레시피 전체 보기`, `재고 등록`, `채팅으로 이동`, `요리 완료`, `전송` 등)은 공통 16px·600 굵기로 표시한다. 정렬·삭제·하단 내비게이션처럼 정보 밀도나 위험도를 구분하는 소형 보조 조작의 글자 크기는 이 규칙으로 일괄 확대하지 않는다.
- 앱의 한글·영문 본문과 제목, 버튼, 입력 필드는 SUIT Regular·Medium·SemiBold·Bold를 사용한다. 기존 굵기 위계는 대응하는 SUIT 굵기로 유지하고 아이콘·이모지처럼 글리프가 없는 문자는 플랫폼 대체 글꼴을 허용한다.
- 전역 비례 축소는 모든 주요 탭과 레시피 상세에 동일하게 적용한다. 재고 목록이나 레시피 상세처럼 본래 콘텐츠가 긴 화면의 내부 스크롤은 유지하되, 기기 크기 때문에 헤더 높이·텍스트 줄바꿈·탭 배치 등 화면 구조가 달라지는 수단으로 스크롤을 사용하지 않는다.
- 하단 내비게이션 순서는 `홈`, `채팅`, `재고`, `레시피`, `조리도구`, `설정`이다.
- 홈을 제외한 주요 화면의 좌상단에는 둥근 사각형 홈 아이콘을 제공한다.
- 각 페이지의 좌상단 제목은 진한 색과 굵은 글꼴로 표시한다.
- 모든 주요 화면은 내용 스크롤을 지원하고 스크롤 바는 숨긴다.

### FR-10. 조리도구

- 조리도구 화면 상단에 얇은 한 줄 텍스트 입력 상자와 `조리도구 입력` 버튼을 둔다.
- 사용자는 `2.5L 냄비`, `계란후라이용 프라이팬`, `전자레인지`, `1인용 에어프라이기`처럼 한 항목을 자연어로 입력한다.
- 등록된 조리도구는 입력 영역 아래에 2열의 정사각형에 가까운 카드로 표시하고, 긴 원문은 카드 안에서 줄바꿈한다.
- 조리도구 카드의 이름은 18px로 읽기 쉽게 표시하며 긴 이름이 잘리지 않도록 카드 높이를 확보한다. 이름 영역은 삭제 버튼 위의 남은 공간에서 가로·세로 중앙 정렬한다.
- 카드에는 별도 장식 아이콘 없이 사용자가 입력한 원문을 우선 표시한다. 붉은색 `삭제` 버튼은 도구명과 분리해 카드 최하단에 고정하여 위험 동작임을 명확히 구분한다.
- AI는 원문을 종류, 용량·크기, 용도·특징으로 구조화하되 원문을 보존한다.
- 레시피 검색과 변형은 보유 조리도구를 필수 제약으로 사용한다.
- 필요한 조리도구가 없으면 안전한 대체 조리법이 검증된 경우에만 보유 도구 기준으로 변형한다.
- 대체가 불가능하면 해당 레시피를 추천하지 않고 가능한 다른 메뉴를 제안한다.
- 냉톡은 누락된 고가 조리도구의 구매를 기본적으로 권하지 않는다.

### FR-11. 알레르기 설정과 적용

- 설정 화면의 `알레르기 항목` 카드는 자유 입력란과 등록 버튼만 제공하고, 그 아래에 `알레르기 목록` 카드를 별도로 배치한다. 전체 법정 알레르기 체크리스트를 필수로 노출하지 않는다.
- 사용자는 실제 알레르기만 항목별로 추가·삭제하며, 비어 있을 때는 의학적으로 알레르기가 없다고 단정하지 않고 `등록된 알레르기 없음`으로 표시한다.
- 목록의 각 항목은 글머리 기호로 구분하고, 우측의 삭제 조작은 조리도구 삭제와 같은 연한 적색 표면·적색 테두리를 사용하되 행 높이에 맞춘 소형 버튼으로 제공한다.
- 내부 정규화·동의어 사전은 사용자가 등록한 항목에 대해서만 활성화한다. 예를 들어 `새우` 등록 시 새우젓·건새우·새우가루 같은 파생 재료를 함께 검사하되, 등록하지 않은 다른 알레르기를 사용자 속성으로 추정하지 않는다.
- 자유 입력이 기존 항목에 명확히 매칭되지 않거나 의미가 여러 개인 경우에만 정규화 결과를 한 번 확인받고 원문을 함께 보존한다.
- 레시피 후보를 만들기 전에 현재 사용자의 등록된 알레르기를 불러와 AI 입력과 후보 검색 필터에 적용한다.
- AI가 생성한 최종 재료 목록은 별도의 알레르기·동의어 규칙 검사도 통과해야 하며 일치 후보는 사용자에게 제시하지 않는다.
- 등록된 정보가 없을 때는 별도 알레르기 필터를 적용하지 않으며 사용자가 설정에서 언제든 추가할 수 있게 한다.
- 심사위원 게스트 데이터에는 `새우` 알레르기를 기본값으로 등록한다.
- 알레르기 설정 변경은 이후 생성·수정되는 제안부터 적용하고 과거 완료 레시피 원문은 변경하지 않는다.

### FR-12. 채팅 기록 관리

- 설정 화면에 `채팅 기록 전체 삭제`를 제공한다.
- 사용자가 버튼을 누르면 모든 채팅 기록이 삭제되고 앱에서 복구할 수 없다는 확인 창을 먼저 표시한다.
- 사용자가 최종 확인하면 현재 사용자 소유의 대화 세션과 메시지를 즉시 삭제하고 빈 채팅 화면으로 이동한다.
- 채팅 기록 전체 삭제는 확정된 재고 변경 이력, 현재 재고, 완료 레시피와 알레르기·조리도구 설정을 삭제하지 않는다.
- MVP에서는 개별 대화 삭제와 개별 메시지 삭제를 제공하지 않는다.

## 6. 제품 규칙

- 심사용 웹은 EAS Hosting의 공개 production URL로 제공하고 사용자의 로컬 컴퓨터 전원·네트워크 상태에 의존하지 않는다.
- MVP는 별도 도메인을 구매하지 않고 EAS Hosting이 발급하는 무료 `*.expo.app` production URL을 사용한다. Android APK를 만든 뒤 동일 origin의 고정 `/install` 페이지에 최신 설치 링크와 안내를 제공하는 작업은 남아 있다.
- 인증·데이터베이스·파일·서버 함수는 Supabase에서 운영하고, OpenAI API 키와 service role 키는 Supabase 서버 secret에만 저장한다.
- 심사 기간에는 Supabase Pro를 사용해 무료 프로젝트의 비활성 자동 중지 위험을 제거하고, 심사 전후 요금제 전환과 복구 절차를 운영 체크리스트로 관리한다.
- Android 심사용 빌드는 EAS Build 내부 배포 프로필의 서명된 APK로 제공할 계획이다. 현재 production 웹을 기본 체험 경로로 유지하며 APK 빌드·실기기 검증·설치 링크 작성은 출시 전 남은 작업이다.
- AI 응답은 재고 DB를 직접 수정할 권한을 갖지 않는다.
- GPT 호출은 인증된 서버 경계를 통해서만 수행하며 OpenAI API 키를 Android·웹 클라이언트에 전달하지 않는다.
- 모든 재고 변경은 검증된 명령과 서버 트랜잭션을 거친다.
- 단위 변환이 안전하지 않으면 자동 합산·차감하지 않는다.
- 원본 단위를 계산 단위로 변환할 때 포장 표기, 사용자 입력 또는 결정적 계산 중 어느 근거를 사용했는지 기록한다.
- 알레르기 정보가 확인되지 않은 재료는 안전하다고 단정하지 않는다.
- AI 응답만으로 알레르기 안전을 판정하지 않고 구조화된 최종 재료 검증을 거친다.
- 권장 소진일은 식품 안전을 보증하는 소비기한과 구분한다.
- 공식 표시 소비기한이 이미 지났다면 추정 규칙으로 날짜를 연장하지 않는다.
- 재고가 부족한데도 `현재 재료만으로 가능`이라고 표시하지 않는다.
- 보유하지 않은 조리도구가 필수인데 안전한 대체법이 없는 레시피를 실행 가능하다고 표시하지 않는다.

## 7. 성공 기준

### MVP 수용 기준

- 심사위원 게스트가 도움 없이 대표 흐름을 완료할 수 있다.
- 구매내역 인식 결과에서 확인 필요 필드만 식별·수정하고, 불필요한 품목을 제외한 뒤 여러 품목을 한 번에 등록할 수 있다.
- 일부 인식 실패 또는 재분석 이후에도 성공 결과와 사용자가 직접 수정한 값이 보존된다.
- 채팅 요청에 현재 재고와 임박 재료가 반영된 레시피가 제시된다.
- 초기 추천은 한 가지이며 후속 채팅으로 조건을 바꾸면 수정된 제안이 제공된다.
- 게스트의 추천·수정 레시피에 새우와 등록된 새우 알레르기 동의 재료가 포함되지 않는다.
- 누락된 필수 재료가 있을 때 구매 후 원래 메뉴를 만드는 선택지와 현재 재료로 가능한 대체 메뉴가 함께 노출된다.
- 요리 완료 전후의 재고 차감값이 일치한다.
- 저장된 레시피에 제공일이 표시되고 상세를 다시 열 수 있다.
- production 웹에서 내부 타이머가 동작한다. Android 시스템 알림·시스템 타이머는 후속 수용 기준으로 분리한다.
- 심사 기간 동안 웹 서비스가 로그인 또는 게스트 진입 가능한 상태로 유지된다.

## 11. 재고 우선 추천·보관 상태 검수 (2026-09-19)

- 추천은 현재 재고만으로 만들 수 있는 레시피를 먼저 제시한다. 공공·공유·Terra 순서나 메뉴명 일치보다 구매 0개가 우선이며, 불가능한 경우에도 구매 필요 품목은 최대 1개다.
- 구매내역, 직접 입력, 채팅으로 추가한 재고는 냉동·냉장·실온 보관 상태를 함께 검수하고 저장한다. 구매내역·직접 입력 검수 화면에서는 보관 상태를 바꿔도 이미 입력된 권장 소진일을 지우지 않고 사용자가 확인·수정할 수 있게 한다. 채팅 재고 추가 검수는 기존의 보관 상태 변경 시 날짜 재확인 흐름을 유지한다.
- 공용 소진일 검색에 신뢰할 근거가 없으면 임의 날짜로 자동 등록하지 않고 사용자가 확인할 빈칸을 제공한다.
